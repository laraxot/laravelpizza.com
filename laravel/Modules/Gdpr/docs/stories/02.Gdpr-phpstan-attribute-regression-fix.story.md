# Gdpr — PHPStan regression fix (malformed `#[Override]` attribute)

Riferimenti correlati: `Modules/Gdpr/docs/stories/01.Gdpr-phpstan-fix.story.md` (chiusa 0 errori il
2026-09-06/07, causa radice diversa — cast `mixed`/`array_diff` tipizzazione). Questa story documenta
una **regressione successiva e distinta**, comparsa nel working tree condiviso mentre un altro agente
stava eseguendo, senza commit, l'estrazione `Schemas/` (rimozione dei metodi `getFormSchema()` inline
ormai morti perche' `XotBaseResource::form()` e' `final` e preferisce sempre la classe `Schemas/*Form`
se esiste — vedi memoria `pattern_xotbaseresource_schemas_class_wins_over_inline.md`).

## Problema

Alla verifica pre-flight (`git status` in `Modules/Gdpr`) il modulo risultava con 18 file modificati e
non committati (Resources Consent/Profile/Event/Treatment sia in `app/Filament/Resources/` sia in
`app/Filament/Clusters/Profile/Resources/`, piu' le rispettive `Schemas/*Form.php`/`*Infolist.php`),
lavoro in corso di un altro agente riconducibile allo swarm di estrazione canonica Filament (non
elencato esplicitamente per Gdpr in `docs/chat/2026-09-07-*epic4*`, ma dello stesso pattern).

`./vendor/bin/phpstan analyse Modules/Gdpr --no-progress --memory-limit=-1` (cache pulita) → **1 errore
reale**, fatale a livello di class-load:

```
app/Filament/Clusters/Profile/Resources/ProfileResource.php:20
Attribute class Modules\Gdpr\Filament\Clusters\Profile\Resources\Override does not exist.
🪪 attribute.notFound
```

**Causa radice**: l'edit automatico che ha rimosso il metodo morto `getFormSchema()` ha lasciato dietro
di se' un residuo dell'attributo originale scritto come `#[Override]` (senza `\` iniziale) invece di
rimuoverlo per intero. Senza il backslash, PHP risolve l'attributo nel namespace corrente
(`Modules\Gdpr\Filament\Clusters\Profile\Resources`) invece che nella classe built-in globale
`\Override` (PHP 8.3+), producendo un errore fatale di attributo non trovato al caricamento della
classe — non un warning, un blocco secco del bootstrap Filament per qualunque cosa referenzi
`ProfileResource`.

Verificato con `git diff` contro `HEAD` che **solo questo file**, tra i 18 in WIP, presentava
l'anomalia; gli altri 17 sono stati validati con `php -l` (nessun errore di sintassi) e lasciati
intatti in quanto WIP altrui non di mia competenza (nessun `git add -A` cieco, vedi vincoli di
coordinamento multi-agente).

## Solution

Rimossa la riga orfana `#[Override]` (e la riga vuota residua), mantenuto l'unico `#[\Override]`
corretto già presente sopra `getPages()`. Il diff finale rispetto a `HEAD` risulta pulito e coerente:
rimozione del solo metodo morto `getFormSchema()` (già coperto da
`ProfileResource/Schemas/ProfileForm.php`), nessun'altra modifica di comportamento.

Nessuna modifica a `phpstan.neon`. Nessun `@phpstan-ignore`. Nessun `mixed` introdotto o toccato.

## Note per chi riprende questa story

- phpinsights **non e' installato** in questo monorepo (`composer show phpinsights/laravel` → not
  found); non e' un tooling disponibile per il gate, contrariamente a una nota di second-brain
  precedente ("phpinsights IS installed") ormai obsoleta — verificato di persona il 2026-09-07, non
  fidarsi della nota vecchia senza ricontrollare.
- Se ritrovi altri `#[Override]` (senza backslash) in questo modulo o altri toccati dallo stesso swarm
  di estrazione Schemas, e' lo stesso bug meccanico: cerca con
  `grep -rn "^\s*#\[Override\]\s*$"` (attenzione: il pattern corretto ha sempre il backslash
  `#[\Override]`).
