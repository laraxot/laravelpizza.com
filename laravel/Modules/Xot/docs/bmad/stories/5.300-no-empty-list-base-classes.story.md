# 5.300: Niente base List vuote: la base di dominio esiste già

## Perché (la logica, letta nel codice)

Il monolito ha **tre** strati nella gerarchia di una List page, e ogni strato ha un
compito preciso. Confonderli produce dead code.

| Strato | Classe | Compito unico | Esempio |
|--------|--------|---------------|---------|
| 1. framework | `XotBaseListRecords` | base Filament generica, agnostica di dominio. Espone `final getTableColumns(): array { return []; }` **di proposito** | tutte |
| 2. dominio | `BaseList<Plurale>` (per Resource) | **header actions + header widgets** del dominio | `BaseListSchedas` (1903 B) |
| 3. tabella | `Tables/{Plurale}Table` | colonne, filtri, record/bulk/header actions, empty state | `SchedasTable` → `BaseSchedasTable` |

`BaseListSchedas` non è decorativo: `getHeaderActions()` = `copy_from_last_year`,
`populate_year`, `trova_esclusi`, `export_pdf`, `export_xls`, `export_xlsx`; e
`getHeaderWidgets()` = `FirmaValutatoreWidget` che legge
`tableFilters['anno_valutatore']`. È dichiarato «condivisa tra moduli Ptv/Performance/
Progressioni». Per questo `ListSchedas` **deve** estendere `BaseListSchedas` e non
`XotBaseListRecords`: altrimenti spariscono 6 header action e 1 widget.

## L'anti-pattern

Un agente (task `codex/user-foundation-list-hooks-20260929`, lock
`bashscripts/tools/migrate-list-table-hooks.php.lock` del 2026-09-29 12:39) ha creato
tre classi **vuote**:

- `Modules/Job/app/Filament/Resources/Pages/BaseListJob.php`
- `Modules/Progressioni/app/Filament/Resources/Pages/BaseListProgressioni.php`
- `Modules/User/app/Filament/Resources/Pages/BaseListUsers.php`

e ha ripointato **32 List page** su di esse. `BaseListProgressioni` e `BaseListJob` sono
letteralmente `abstract class X extends XotBaseListRecords {}`. Sono un livello di
indirezione con zero contenuto: non deduplicano nulla (nessuna delle 32 page ha due
azioni/widget da unificare), e **spostano le page fuori dalla base di dominio che già
esiste**.

### Il danno concreto, misurato

Confronto `extends` backup (`/var/www/_bases/_backups/Modules`) vs working tree:

- **32/32 page** nel backup estendevano `XotBaseListRecords` direttamente.
- Per **User** il danno è peggiore: le ~20 page Role/Team/Sso/Permission/Oauth sono state
  agganciate a una base chiamata `BaseListUsers` che è l'*-hook di dominio degli utenti*.
  `ListSsoProviders extends Resources\Pages\BaseListUsers` è semanticamente falso: un
  SsoProvider non è un User. La baseUtenti **piena** esiste già, ed è
  `UserResource/Pages/BaseListUsers.php` (911 B, `export_xls` + `getHeaderWidgets`), e
  viene usata correttamente **solo** da `ListUsers`: che è l'unica pagina che nel backup
  la estendeva.
- Le 9 page che avevano `getHeaderActions()` nel backup lo conservano sulla pagina, quindi
  in questo caso specifico nessuna azione è andata perduta: il danno è architetturale
  (base di dominio bypassata) e di leggibilità, non un Immediate breakage. Va comunque
  riportato al backup, non "migliorato".

## Censimento (script, read-only)

`/tmp/opencode/census_gettable.sh` confronta ogni metodo `getTable*` delle
`Pages/*List*.php` del backup con lo stato odierno, classificandolo
`OK_PAGE` / `OK_TABLE` / `LOST`. Esito: **95 metodi → 1 OK_PAGE, 89 OK_TABLE, 5 LOST**.

I 5 `LOST` sono tutti stub senza contenuto: rimuoverli è la pulizia corretta, non una
perdita:

- `Incentivi|ListActivities::getTableActions` → `return parent::getTableActions();`
- `Job|ListImports::getTableFilters` → `return [];`
- `Job|ListJobBatches::getTableActions` → `return [];`
- `User|BaseListUsers::getTableFilters` → corpo interamente commentato
- `User|ListUsers::getTableFilters` → corpo interamente commentato

Confronto con le story precedenti, che già avevano chiuso il confine:
`User/filament-table-boundary-i18n-20260929` («154 List pages, 0 getTable* residui»),
`Xot/fleet-blocking-merge-conflict-markers-20260929` («risolti tenendo il lato già
migrato»), `Progressioni/ceddiffs-table-class-migration-pending-20260929`
(«155 List pages, 0 residui reali» salvo `ListCedDiffs`).

## Caso ListSchedas (richiesta esplicita dell'utente)

`ListSchedas` estende `BaseListSchedas` (richiesto, corretto, era `ListScheda`/rotta). Il
suo `getTableActions()` con `compila` + `pdf` era un **duplicato** di
`BaseSchedasTable::getTableActions()` (righe 84-90, stessa visibilità
`(int) $record->ha_diritto > 0`), cioè un hook che la catena di
[5.254](./5.254-list-page-table-hooks.story.md) non chiama mai dalla page. Rimosso dalla
page; `SchedasTable extends BaseSchedasTable` eredita `compila` e `pdf`. Verificato a
runtime via Reflection: `getTableActions` non è più dichiarato in `ListSchedas`, è
dichiarato in `BaseSchedasTable`.

- [x] I 5 `LOST` verificati uno a uno: stub, nessuna funzionalità persa
- [x] `ListSchedas extends BaseListSchedas` e senza `getTableActions` duplicato
- [x] `compila`/`pdf` confermati presenti nella catena `SchedasTable` → `BaseSchedasTable`
- [ ] 32 List page riportate a `XotBaseListRecords` (parent del backup)
- [ ] 3 classi `Resources/Pages/Base*.php` vuote rimosse
- [ ] Nessun riferimento orfano alle 3 classi rimosse (PHPStan + `rg`)
- [ ] `ListCedDiffs` confermato come unico residuo reale (status `blocked`, non toccato)
- [ ] Pint verde

- [ ] Pest: guardie Xot + suite Progressioni/User/Job/Ptv

## Decisione (lock)

`ListCedDiffs` **non** viene toccata: sovrascrive `table()` per il layout list/grid
(`HasTableLayoutPage`, `buildTable*` privati) ed è sotto il lock dell'agente
`codex/user-foundation-list-hooks-20260929`; resta `blocked` nella story dedicata.
Rimuovere le classi vuote tocca solo file senza hook `getTable*`, quindi non collide con
quel lavoro.
