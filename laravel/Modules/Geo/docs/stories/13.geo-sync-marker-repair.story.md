# 13 - Geo: riparazione dei marcatori di conflitto lasciati dal sync

## Obiettivo

`phpstan analyse Modules` non partiva perché 15 file PHP di Geo contenevano `<<<<<<<` / `=======` / `>>>>>>>` annidati,
prodotti da `bashscripts/git/subtrees/merge_remote_repo_2.sh` (`commit -am .`). Obiettivo: lasciare per ogni file una
versione che fa quello per cui il file esiste, senza scegliere un lato a caso e senza perdere righe uniche.

Metodo: per ogni file si sono letti i blocchi, si è cercato chi lo chiama e cosa si aspettano i test, e si è provato che
l'insieme delle righe uniche dei due lati coincide con una revisione integra della storia del repository root
(`6e32612c` del 24-Nov 17:48; `eddac6d31` per `OsmProxyTest`, l'ultima versione senza marcatori).

## File in scope e risoluzione

Scopo di ogni file, chi lo usa e dettaglio della risoluzione: `../geo-sync-marker-repair.md` (tabella unica, non si
ripete qui). In sintesi: in tutti i 15 file i due lati differivano solo nella forma (Pint contro php-cs-fixer: docblock
`@param  tipo  $nome` o con riga vuota prima di `@return`, `new Foo;` o `new Foo()`, `!== null` o `null !==`,
`{@see HasCoordinatePicker}` con `use` o FQCN). Nessuna logica diversa.

| Gruppo | File | Risoluzione |
|---|---|---|
| Produzione | `GeoMapDatasetAction`, `GeoMapDataset`, `HasCoordinatePicker`, `BaseGeoService`, `GeoDataService`, `GeoDataValidator`, `GeoService`, `GoogleMapsService` | stile modulo, righe uniche dei due lati tutte conservate |
| Produzione | `CoordinatePickerHelpers` | docblock con FQCN; tolto il `use HasCoordinatePicker` rimasto da solo (usato solo dal lato scartato) |
| Test | `OsmProxyTest` | `eddac6d31`: 8 test, 7 chiamate `->group(...)` con tag `->group('GEO-...-INV-n')`; il file era a 388 righe con 140 marcatori |
| Test | `GoogleMapsServiceElevationStub`, `GetAddressDataFromFullAddressActionTest`, `ComuneModelTest`, `HereServiceTest`, `ServicesTest` | stile modulo / `use TestCase` |

Righe scartate (tutte equivalenti a una riga tenuta): `uses(\Modules\Geo\Tests\TestCase::class);` (in `ServicesTest` e
`ComuneModelTest`, sostituita da `uses(TestCase::class);` con il `use` già presente), `(new X)->...` (in
`GetAddressDataFromFullAddressActionTest`, sostituita da `(new X())->...`), `) {` + `}` e `null !== $this->exception`
(in `GoogleMapsServiceElevationStub`, sostituite da `) {}` e `$this->exception !== null`), e le varianti `new X;`.

## Verifica

- `git grep -lIE '^(<<<<<<<|>>>>>>>) ' -- 'laravel/Modules/Geo/*.php' 'laravel/Modules/Geo/*.blade.php'`: 0 file.
- `php -l` su ogni file tracciato `Modules/Geo/**/*.php`: nessun errore.
- Import e classi padre dei 15 file risolvono via autoload (script di controllo su `use Modules\...` e `extends`).
- Confronto con la revisione integra: righe diverse solo di forma (`diff -w` contro `6e32612c`).
- PHPStan: non eseguito in questa corsia (il boot dipende dalle altre corsie); lo lancia l'orchestratore.

## Fuori scope, da sapere

- Altri processi scrivevano in parallelo su Geo durante la corsia (risoluzioni identiche nella sostanza; `CoordinatePickerHelpers`
  ha avuto modifiche non mie a `reverseGeocode`, con `@see` all'ADR sul provider preferito).
- `Support/GeoMapDataset` non ha chiamanti: la sua versione a Action (`GeoMapDatasetAction`) è quella usata.
- Il modulo `laraxot/module_geo_fila5` ha gli stessi marcatori su `laraxot/dev`: ripulirlo là.
