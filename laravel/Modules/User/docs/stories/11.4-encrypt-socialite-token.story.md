# Story 11.4: cifrare il token Socialite a riposo

## Contesto (audit BMAD "perfezione assoluta", 2026-09-22)

`laravel/Modules/User/app/Models/SocialiteUser.php`: la proprieta' `token` e'
`fillable` ma **nessun cast** (`grep -n "casts\|token\|encrypted"` → solo docblock
e fillable, nessun `'token' => 'encrypted'`). La colonna `socialite_user.token`
(TEXT) contiene quindi il token OAuth del provider esterno in chiaro.

**Impatto:** chiunque abbia accesso in lettura al database (dump, backup,
accesso diretto, injection SQL residua altrove) ottiene token OAuth validi
utilizzabili per impersonare l'utente presso il provider esterno.

## User story

Come utente che effettua login social,
voglio che il mio token OAuth non sia leggibile in chiaro nel database,
cosi' che un accesso non autorizzato al DB non comprometta il mio account
esterno.

## Acceptance criteria

- [ ] `SocialiteUser` dichiara `protected function casts(): array { return
      ['token' => 'encrypted']; }` (o equivalente, coerente con la convenzione
      Laravel in uso nel resto del modulo).
- [ ] Migration additiva per ricifrare i valori esistenti in chiaro (mai un
      wipe/rewrite distruttivo: leggere il valore in chiaro, riscriverlo
      cifrato, riga per riga, con verifica prima/dopo).
- [ ] Verificato che nessun altro punto del codice legge `->token` assumendo
      valore in chiaro senza passare dal cast Eloquent (query raw, log,
      export).
- [ ] Test che verifica: lettura via query raw (`DB::table('socialite_user')
      ->value('token')`) non espone il valore in chiaro; lettura via model
      Eloquent (`SocialiteUser::find($id)->token`) restituisce il valore
      corretto decifrato.

## Piano di verifica

1. Pest: creare `SocialiteUser` con token noto, leggere via query raw → valore
   diverso dal chiaro; leggere via model → valore == originale.
2. Verifica migration di re-cifratura su un set di righe di test (mai su dati
   di produzione senza backup/verifica preventiva: vincolo dati sacri).
