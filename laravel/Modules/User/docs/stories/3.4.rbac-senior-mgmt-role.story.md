# 3.4: RBAC: Senior Mgmt role (approve Progressioni)

**Story ID:** 3.4
**Epic:** 3: Access Control & Security
**Slug:** rbac-senior-mgmt-role
**Status:** backlog

## Story

As a senior manager (director-level approver),
I want a narrowly-scoped permission to approve Progressioni career-progression records,
so that approval authority stays restricted to designated decision-makers without granting me full admin access.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A new Spatie role, `senior_mgmt`, is seeded via an additive migration with exactly one permission: `approve progressioni`. [Inference: see Dev Notes: FR-005's formal role list (`staff`, `evaluator`, `hr_admin`, `finance`, `pa_admin`) does not name this role verbatim; it is derived from FR-009's "manager/director" approver requirement.]
2. `Modules/User/app/Policies/ProgressioniApprovalPolicy.php`'s `approve()` method returns `true` only for `senior_mgmt` and `pa_admin` roles; `false` for `evaluator`, `staff`, `hr_admin`, `finance`. [Source: prd.md#NFR-SEC-003: "Matrix: create, read, update, approve per role per resource"]
3. `senior_mgmt` role is denied all Scheda actions (`create`/`update`/`delete`/`view`) and all `UserPolicy` actions: it is scoped strictly to Progressioni approval, not a general elevated role. [Source: prd.md#NFR-SEC-003: least-privilege matrix intent; Source: prd.md#FR-005: role separation]
4. The Filament Progressioni approve action (Epic 1 scope, `Modules/Progressioni/app/Filament/Resources/ProgressioniResource.php`) is hidden/disabled for any Filament user lacking `approve progressioni` permission: this story delivers the policy gate the Epic 1 resource must call; it does not build the approval workflow UI itself. [Source: architecture.md#api-specifications: "Approval Link Route: view/approve Progressioni with signed URL and Activity logging. Auth: signed link plus policy validation."]
5. Role+action matrix test proves: `senior_mgmt` CAN approve Progressioni; `senior_mgmt` CANNOT create/update/delete Scheda or manage users; every other role except `pa_admin` is denied approve. [Source: prd.md#NFR-SEC-003: "Test: 100% coverage (every role tested on every action)"]

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Role-naming gap flagged:** FR-005's formal acceptance criteria enumerate exactly five roles: `staff`, `evaluator`, `hr_admin`, `finance`, `pa_admin`: with `pa_admin` holding "all access." [Source: prd.md#FR-005] There is no `senior_mgmt` (or equivalent) role in that list. The story title in epics.md ("RBAC: Senior Mgmt role (approve Progressioni)") derives instead from FR-009's description: "Senior management approve career progressions... send to manager/director with link to inline approval form." [Source: prd.md#FR-009] `[Inference]` This story treats `senior_mgmt` as a sixth, narrowly-scoped role added on top of the FR-005 matrix specifically to satisfy FR-009's approver concept without overloading `pa_admin` (which already has blanket access): consistent with NFR-SEC-003's per-role, per-action permission matrix philosophy. If product intends `pa_admin` alone to cover this approver, the dev agent should raise that as a scope question before implementing a new role.
- **FR-009 is COULD/Phase 1.5, out of scope here:** the full approval workflow (create progression, email with inline approval link, status transitions pending→approved→enacted) is Epic 1 Story 1.9, not this story. [Source: prd.md#FR-009: "Priority: Phase 1.5 (MVP without; polish release with)"] This story delivers only the RBAC gate that 1.9 will call.
- **Architecture grounding for the approval route:** "Approval Link Route: view/approve Progressioni with signed URL and Activity logging. Auth: signed link plus policy validation." [Source: architecture.md#api-specifications] The policy validation half is exactly `ProgressioniApprovalPolicy::approve()`.
- **Data model:** `ProgressioniApproval`: `id`, `tenant_id`, `employee_id`, `new_role`, `salary_step`, `status`, `approved_at`; "audited status transitions." [Source: architecture.md#data-model: `ProgressioniApproval` row]
- **ADR grounding:** ADR-004 requires Laravel policies for resource actions in addition to Spatie roles: `ProgressioniApprovalPolicy` is this story's policy artifact. [Source: architecture.md#adr-004]
