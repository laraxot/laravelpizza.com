# 3.1: RBAC: Evaluator role (create/edit own Scheda)

**Story ID:** 3.1
**Epic:** 3: Access Control & Security
**Slug:** rbac-evaluator-role
**Status:** backlog

## Story

As an evaluator,
I want to create and edit Scheda evaluation records via a permission I hold (not ad-hoc admin access),
so that I can complete evaluations for my PA without needing pa_admin privileges, and without being able to approve, delete, or manage users.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A migration seeds all five roles required by FR-005: `staff`, `evaluator`, `hr_admin`, `finance`, `pa_admin`: plus the base permission matrix, using Spatie Permissions. [Source: prd.md#FR-005: "Setup: role seeding + permission matrix in migration"]
2. `evaluator` role is granted `create scheda` and `update scheda` permissions; `SchedaPolicy::create()` and `SchedaPolicy::update()` return `true` for users with the `evaluator` role. [Source: prd.md#FR-005: "evaluator (CRUD all Scheda)"]
3. `evaluator` role does NOT receive `delete scheda` or `approve progressioni` permissions: `SchedaPolicy::delete()` returns `false` for `evaluator`. [Source: prd.md#FR-005 role matrix; Source: prd.md#NFR-SEC-003: "Matrix: create, read, update, approve per role per resource"]
4. `evaluator` role has no access to `Modules/User/app/Filament/Resources/UserResource.php` (user management is `pa_admin`-only, delivered in 3.3). [Source: prd.md#FR-005: role separation]
5. A role+action test matrix proves: evaluator CAN create/update Scheda; evaluator CANNOT delete Scheda, approve Progressioni, or manage users; staff/finance CANNOT create/update Scheda. [Source: prd.md#FR-005: "Test: 100% coverage of role+action combos (staff cannot create, evaluator cannot approve, etc.)"; Source: prd.md#NFR-SEC-003: "Test: 100% coverage (every role tested on every action)"]

## Tasks / Subtasks

  - [ ] Define permission strings: `create scheda`, `update scheda`, `delete scheda`, `view scheda`, `approve progressioni`, `manage users` (AC: #1, #2, #3)
  - [ ] Assign `create scheda` + `update scheda` to `evaluator` role (AC: #2)

- [ ] Write role+action matrix test covering evaluator, staff, finance against create/update/delete/approve/manage-users (AC: #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Architecture component:** This story implements the "Access Control (`User`, `Tenant`)" component: "Auth, roles, permissions, tenant policy" via "Laravel auth, Spatie roles, policies, RLS policies." [Source: architecture.md#component-design: Access Control row]
- **ADR grounding:** ADR-004 mandates "Spatie Permissions for roles/permissions, Laravel policies for resource actions." Every new resource story must include role matrix tests: this story is the first to establish that pattern for Scheda. [Source: architecture.md#adr-004]
- **FR-005 role list is authoritative:** `staff`, `evaluator`, `hr_admin`, `finance`, `pa_admin`. [Source: prd.md#FR-005] Note: the PRD's illustrative Epic 3 user story (Story 3.1 example) describes evaluator as "CRUD own dept Scheda," but the formal FR-005 acceptance criteria state "evaluator (CRUD all Scheda)" with no department scoping. This story implements the formal AC (CRUD all, within tenant); department-level scoping is not in scope and is not required by any cited AC. [Source: prd.md#FR-005; cf. prd.md: Epic 3 Story 3.1 narrative example]
- **Data model:** `User` has `tenant_id`; roles are attached via Spatie (not a raw column). [Source: architecture.md#data-model: `User` row: "roles via Spatie; belongs to Tenant"]
- **Stack constraint:** Spatie Permissions is a fixed dependency per the architecture technology stack (`AuthZ | Spatie Permissions + policies + RLS`). [Source: architecture.md#technology-stack]
- [Inference] Permission string naming (`create scheda`, `update scheda`, etc.) follows Spatie's conventional `verb noun` format; no PRD/architecture source dictates exact string names, so the dev agent may adjust names as long as the role-to-action matrix in AC #2/#3/#5 holds.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature/policy tests (Pest), no browser/e2e needed for this story.
- **Fixtures:** Use model factories for `User` with each of the 5 roles assigned via Spatie `assignRole()`. Use a `Scheda` factory (Epic 1 scope) or a minimal stub model if Epic 1 has not yet landed: coordinate via Blocked-by.
- **Scenarios to prove each AC:**
  - AC #1: assert all 5 roles exist after migration runs; assert permission matrix rows exist.
  - AC #2: `$this->assertTrue($evaluatorUser->can('create', Scheda::class))` and same for `update`.
  - AC #3: `$this->assertFalse($evaluatorUser->can('delete', Scheda::class))`; assert evaluator lacks `approve progressioni` permission.
  - AC #4: assert `UserResource::canAccess()` (or equivalent Filament policy gate) is `false` for evaluator.
  - AC #5: parametrized/data-provider test iterating [role × action] combinations, asserting expected boolean per the role matrix.
- **Edge cases:** user with NO role assigned (should fail all Scheda actions); user with multiple roles (e.g. evaluator + finance): verify permissions union correctly, not silently overridden.
