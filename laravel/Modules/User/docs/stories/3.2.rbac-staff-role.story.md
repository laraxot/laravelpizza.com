# 3.2: RBAC: Staff role (read-only own Scheda)

**Story ID:** 3.2
**Epic:** 3: Access Control & Security
**Slug:** rbac-staff-role
**Status:** backlog

## Story

As a staff member,
I want to view only my own Scheda evaluation records in read-only mode,
so that my personal evaluation data stays private from other staff and I cannot accidentally modify a record I do not own.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `staff` role is granted `view scheda` permission scoped to records where the Scheda's employee matches the authenticated user; `SchedaPolicy::viewAny()` and `SchedaPolicy::view()` return `true` only for the staff member's own record(s). [Source: prd.md#FR-005: "staff (read own Scheda)"]
2. `SchedaPolicy::create()`, `::update()`, `::delete()` return `false` for the `staff` role. [Source: prd.md#FR-005: role matrix; Source: prd.md#NFR-SEC-003: "Matrix: create, read, update, approve per role per resource"]
3. A staff member attempting to view a Scheda record belonging to a different employee is denied by the policy (403 / `AuthorizationException`), not silently redirected or shown an empty state that leaks existence of the record. [Source: prd.md#NFR-SEC-002: "Scopes: tenant_id..., user_role (staff read own; evaluator read dept; admin read all)"]
4. `staff` role has no access to `Modules/User/app/Filament/Resources/UserResource.php`, Sigma resources, or the Progressioni approve action. [Source: prd.md#FR-005: role separation]
5. Role+action matrix test proves: staff CAN view own Scheda; staff CANNOT view another employee's Scheda, create, update, delete, or approve anything. [Source: prd.md#FR-005: "Test: 100% coverage of role+action combos (staff cannot create...)"]

## Tasks / Subtasks

- [ ] Assign `view scheda` permission to the `staff` role in the roles/permissions seed established by 3.1: read-only, no write actions (AC: #1, #2)
- [ ] Add `view()` and `viewAny()` methods to `Modules/User/app/Policies/SchedaPolicy.php`, scoping staff visibility to `scheda.employee_id === user.employee_id` (or the tenant-resolved employee identity) (AC: #1, #3)
- [ ] Confirm `create()`/`update()`/`delete()` on `SchedaPolicy` already default-deny for staff (no permission granted in 3.1's matrix) and add an explicit test asserting this (AC: #2)
- [ ] Add `isStaff(): bool` helper to `Modules/User/app/Models/User.php` (AC: #1)
- [ ] Verify `UserResource`, Sigma resources, and Progressioni approve action are unreachable for `staff` role (policy-gate check, not full UI test) (AC: #4)
- [ ] Write role+action matrix test extending 3.1's test pattern with staff-specific view scoping cases (AC: #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Architecture component:** Same Access Control component as 3.1: "Auth, roles, permissions, tenant policy" via Spatie roles + Laravel policies. [Source: architecture.md#component-design: Access Control row]
- **RLS is a backstop, not the only control:** the policy-level check in AC #3 is the application-layer half of defense-in-depth; the database-layer half (PostgreSQL RLS) is delivered in 3.8 and validated separately. [Source: architecture.md#trade-off-analysis: "RLS plus policies vs policies only: Chosen defense-in-depth... Mitigation: require role/RLS matrix tests for secured stories."]
- **Data model:** staff visibility scoping keys off `Scheda.employee_id` and `User.tenant_id`/employee identity fields. [Source: architecture.md#data-model: `Scheda` row: `employee_id`; `User` row: `sigma_employee_id`]
- **FR-005 formal AC is authoritative:** "staff (read own Scheda)": no department or team-wide staff visibility is in scope. [Source: prd.md#FR-005]
- **NFR-SEC-002 scope alignment:** RLS design explicitly names "staff read own" as one of three role scopes (staff/evaluator/admin) that must be enforced consistently between policy and RLS layers: this story is the policy half for the staff scope. [Source: prd.md#NFR-SEC-002]
- [Inference] "Denied, not silently redirected" in AC #3 is a security-hygiene inference (avoid information leakage via inconsistent 404-vs-403 behavior); not verbatim in the PRD, but consistent with NFR-SEC-002's "no bypass" intent.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature/policy tests (Pest). No e2e required for this story (staff portal UI itself is 3.6).
- **Fixtures:** `User` factory with `staff` role assigned; two `Scheda` factories: one belonging to the staff user's employee identity, one belonging to a different employee in the same tenant.
- **Scenarios to prove each AC:**
  - AC #1: staff user `can('view', ownScheda)` is `true`.
  - AC #2: staff user `can('create'|'update'|'delete', Scheda::class)` is `false`.
  - AC #3: staff user `can('view', otherEmployeeScheda)` is `false`; attempt via controller/Filament resource returns 403, not a soft-fail.
  - AC #4: staff user denied on `UserResource`, Sigma resource, and Progressioni approve action policy gates.
  - AC #5: full role/action data-provider matrix, staff row only (evaluator/admin rows owned by 3.1/3.3, do not duplicate).
- **Edge cases:** staff user with no linked employee record (should deny all Scheda views, not error); staff user viewing own Scheda across a soft-delete boundary (Epic 1 scope: confirm policy still denies once record is soft-deleted, if reachable at all).
