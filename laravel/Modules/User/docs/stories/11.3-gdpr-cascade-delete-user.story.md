# Story 11.3: cascade delete GDPR-compliant

## Contesto (audit BMAD "perfezione assoluta", 2026-09-22)

Nessun modulo `Gdpr` esiste in questo repo (`find laravel/Modules -iname
"*gdpr*"` → vuoto). L'unico punto di cancellazione e'
`laravel/Modules/User/app/Actions/User/DeleteUserAction.php`:

```php
$this->authGuard->logout();   // solo il guard/sessione corrente
$user->delete();               // SoftDeletes commentato in BaseUser.php → hard delete
```

Le migration di `oauth_access_tokens`, `oauth_auth_codes`, `socialite_user` usano
`$table->foreignIdFor($userClass,'user_id')` **senza** `.constrained()`/
`.cascadeOnDelete()`: nessun vincolo FK reale. `UserObserver::deleting()` pulisce
solo il personal team. `RevokeAllUserTokensAction.php` esiste gia' ma non e' mai
chiamata da `DeleteUserAction` (unico consumer oggi: azione manuale admin su
`OauthAccessTokenResource`).

**Impatto:** dopo "elimina account" restano righe orfane con PII (email, nome,
avatar, token) in `profiles`, `socialite_user`, `authentications`,
`model_has_role`; token OAuth/Passport restano `revoked=false`.

## User story

Come utente che cancella il proprio account,
voglio che i miei dati collegati (token, social login, log di autenticazione)
vengano davvero rimossi o anonimizzati,
cosi' che non restino PII orfane nel database.

## Acceptance criteria

- [ ] `DeleteUserAction` invoca `RevokeAllUserTokensAction` per l'utente
      cancellato prima/durante la cancellazione.
- [ ] `SocialiteUser` collegati all'utente vengono rimossi o anonimizzati
      (decisione da esplicitare: cancellazione hard su questi dati e'
      accettabile perche' non servono ad audit trail, a differenza di
      `AuthenticationLog`).
- [ ] `AuthenticationLog` collegati: anonimizzati (non cancellati, se servono
      per audit di sicurezza aggregato): decisione da documentare nella story
      al momento dell'implementazione, coerente con eventuali requisiti di
      compliance del progetto ospite.
- [ ] Pivot di ruolo (`model_has_role`) per l'utente cancellato rimossi.
- [ ] Nessuna riga orfana rilevabile con una query di verifica dopo la
      cancellazione (query read-only di controllo, da includere nel test).
- [ ] Comportamento testabile e testato: creare utente con token/social/log
      collegati, cancellarlo, verificare zero righe residue nelle tabelle
      collegate.
- [ ] Non sostituisce ne' rimanda la garanzia strutturale a livello schema
      (story 15.2, FK cascade): questa story copre il livello Action, 15.2
      copre il livello DB come safety-net (ADR-P004 in
      perfection-architecture.md).

## Piano di verifica

1. Pest: factory utente + token OAuth + SocialiteUser + AuthenticationLog +
   ruolo assegnato → `DeleteUserAction::execute()` → assert zero righe residue
   nelle 4 tabelle collegate.
2. Nessuna `RefreshDatabase` (vincolo di progetto): usare factory/cleanup
   espliciti coerenti con le altre suite del modulo.
