# 6.2: User invite workflow: admin creates staff + evaluators

**Story ID:** 6.2
**Epic:** 6: Setup & Operations
**Slug:** user-invite-workflow
**Status:** backlog

## Story

As a PA admin or HR admin,
I want to invite individual users or upload a CSV batch of staff and evaluators,
so that new PA employees get pending accounts without me manually creating each one in Filament.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `pa_admin` or `hr_admin` can invite a single user via a Filament form (email, name, intended role, department) from the Setup module. [Source: prd.md#FR-010]
2. The Setup module accepts a CSV upload (columns: email, name, role, department) and creates one pending user invite per valid row. [Source: prd.md#FR-010]
3. Invited users are persisted with no password set and an `invited_at` timestamp; a queued notification carrying a signed acceptance link is dispatched (not sent synchronously in the request). [Source: architecture.md#adr-005]
4. Row-level validation: a row with a missing/malformed email, or an email already present in the tenant, is rejected individually with a per-row error message; one bad row does not abort the rest of the batch. [Source: prd.md#FR-010]
5. Every created user record has `tenant_id` set to the current PA tenant; cross-tenant creation is not possible. [Source: architecture.md#data-model] [Source: prd.md#FR-005]

## Tasks / Subtasks

- [ ] Build `InviteUsers` Filament page (single-invite form: email, name, intended role, department) (AC: #1)
- [ ] Add CSV upload field + `ImportUserCsvAction` that parses rows into a validated collection (AC: #2, #4)
- [ ] Implement `CreateInvitedUserAction`: creates `User` row with null password, `invited_at` timestamp, `tenant_id` from current tenant context, `intended_role` column stored as plain string (role assignment happens in story 6.3, not here) (AC: #3, #5)
- [ ] Implement `UserInvitedNotification` (queued `ShouldQueue` notification) with a signed acceptance URL (AC: #3)
- [ ] Per-row validation: reject missing/malformed email and duplicate-in-tenant email, collect errors without aborting the batch (AC: #4)
- [ ] Gate the page to `pa_admin`/`hr_admin` only, consistent with 6.1's access pattern (AC: #1)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Source requirement**: FR-010 AC bullet "Import: bulk user CSV (email, name, role, department)" is the literal spec for the CSV columns and single-invite fields used here. [Source: prd.md#FR-010]
- **Async work pattern**: "Use Laravel queued jobs, scheduled commands, and retry/backoff policies for `SendSchedaEmail`, `GenerateSchedaPdf`, `SyncSigmaEmployees`, `ReconcileSigmaRecords`, and `ArchiveActivityLogs`." The invite notification is the same class of "send email" async work and must not block the request thread; the ADR's named job list does not include invites, so this is an extension of the same pattern, not a listed job. [Source: architecture.md#adr-005] [Inference]
- **Data model**: `User` entity attributes are `id`, `tenant_id`, `email`, `name`, `sigma_employee_id`; "roles via Spatie; belongs to Tenant." An invited-but-unassigned user is still a `User` row: role assignment is deferred to story 6.3, this story only creates the row and stores the requested role as data, not as an assigned Spatie role. [Source: architecture.md#data-model]
- **Tenant/RBAC constraint**: "Multi-tenant: one database per PA; tenant_id filter on all queries." Every insert in this story must carry the current tenant's `tenant_id`. [Source: prd.md#FR-005]
- **Scope boundary vs Epic 3**: `Modules/User/app/Models/User.php`, `Modules/User/app/Filament/Resources/UserResource.php`, and `Modules/User/app/Policies/` are owned by Epic 3 (Access Control) per the sharding context's Owned File/Module Scope table. This story reads/writes `User` rows through the existing model but does not modify any file under `Modules/User/`; all new code lives under `Modules/User/`. [Source: sharding-context.md#epic-3] [Inference: scope-boundary application, not a direct quote]
- **Column addition risk**: if the `User` migration does not already have `invited_at` / `intended_role` columns, this story needs a migration. Per project migration policy, additive-only columns via `tableUpdate()` with `hasColumn()` guards on the `User` model's migration: this touches a migration file under `Modules/User/database/migrations/`, which is Epic 3's owned path. Flag this as a coordination point for the orchestrator rather than silently editing Epic 3's scope. [Inference]

## Testing

- **Test types**: Filament/Livewire feature test for the single-invite form; feature test for CSV import with `Illuminate\Http\UploadedFile::fake()`; unit test for `ImportUserCsvAction` row validation; `Notification::fake()` + `Queue::fake()` assertions for the invite notification.

- **AC #3**: assert `UserInvitedNotification` is queued (`Notification::assertSentTo` with `Queue::fake` or `ShouldQueue` assertion), not sent synchronously; assert created user has `password` null and `invited_at` set.
- **AC #5**: create two tenants, run an invite/import in tenant A, assert zero new `User` rows appear scoped to tenant B.
- **Fixtures**: `User`/`Tenant` factories; CSV fixture files under `Modules/User/tests/Fixtures/Setup/` (valid batch, mixed-validity batch).
- **Edge cases**: empty CSV, CSV with only a header row, 0-byte upload, email casing duplicates (`A@x.com` vs `a@x.com`), department left blank (should still create user per FR-010's optional treatment: verify against wizard field requiredness before asserting either way).
