# 6.3: Permission seeding: auto-assign roles to invite batch

**Story ID:** 6.3
**Epic:** 6: Setup & Operations
**Slug:** permission-seeding-invite-batch
**Status:** backlog

## Story

As a PA admin,
I want the invite batch's requested roles automatically validated and assigned once I confirm them,
so that invited staff and evaluators land in the system already permissioned, without a separate manual RBAC pass.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. For an invite batch created by story 6.2, an action reads each invited user's stored `intended_role` string and validates it against the five roles seeded in 6.1 (`staff`, `evaluator`, `hr_admin`, `finance`, `pa_admin`). [Source: prd.md#FR-005] [Source: prd.md#FR-010]
2. Unrecognized role strings are excluded from auto-assignment and listed in a preview/dry-run report shown to the admin before anything is committed. [Source: prd.md#FR-010]
3. On confirmation, each valid invited user is assigned exactly one Spatie role matching their intended role via `assignRole()`; re-running the action on an already-assigned user is idempotent (no duplicate role rows for that user). [Source: prd.md#FR-005] [Source: architecture.md#adr-004]
4. Role assignment is scoped to the current PA tenant; no user outside the invite batch's tenant is modified. [Source: architecture.md#data-model] [Source: prd.md#FR-005]
5. An Activity log entry (`action = role_change`) is written for each assignment, capturing the affected user, the assigned role, and the admin who confirmed the batch. [Source: architecture.md#adr-009] [Source: prd.md#FR-006]

## Tasks / Subtasks

- [ ] Implement `AssignRolesToInviteBatchAction::preview()`: validates each invited user's `intended_role` against the seeded role set, returns a report of assignable vs. unrecognized rows, commits nothing (AC: #1, #2)
- [ ] Implement `AssignRolesToInviteBatchAction::commit()`: calls `assignRole()` per valid user, guarded so a user already holding that role is skipped, not duplicated (AC: #3)
- [ ] Scope every read/write in the action to the invite batch's `tenant_id` (AC: #4)
- [ ] Emit an `Activity` entry per successful assignment with `action = role_change`, `user_id`, new role, and the confirming admin's user id (AC: #5)
- [ ] Surface the preview report on the Filament page (from `InviteUsers`/wizard flow) so the admin sees unrecognized roles before confirming (AC: #2)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Source requirement**: FR-010 AC bullet "Verification: preview + dry-run before save" is the direct spec for the preview/commit split in this story: the dry-run must show what will change before it changes. [Source: prd.md#FR-010]
- **Role set**: "Roles: staff (read own Scheda), evaluator (CRUD all Scheda), hr_admin (Sigma + settings), finance (reports only), pa_admin (all access)." These are the only valid `intended_role` values this action may assign; anything else is unrecognized by definition. [Source: prd.md#FR-005]
- **RBAC decision**: "Use Spatie Permissions for roles/permissions, Laravel policies for resource actions... No client-side service role credentials." Assignment must go through Spatie's `assignRole()`/`hasRole()` API, not a hand-rolled pivot write. [Source: architecture.md#adr-004]
- **Audit requirement**: "Create Activity entries from domain events for create/update/delete/approve/email/export/role-change/sync actions. Activity rows are append-only." Role assignment is explicitly named (`role-change`) as an event that must produce an Activity row. [Source: architecture.md#adr-009]
- **FR-006 test coverage note**: "Triggered by: Scheda model events (created/updated/soft-deleted), ProgressioniApproval events, user login (optional)" lists Scheda/Progressioni/login as Activity triggers but does not explicitly list role_change in FR-006's own bullet list: the `role_change` action name and requirement come from ADR-009's decision text above, not from FR-006's bullets. Cited separately so the dev tool does not conflate the two. [Source: prd.md#FR-006] [Inference: reconciling FR-006 and ADR-009]
- **Idempotency requirement**: derived from FR-005's "Test: 100% coverage of role+action combos" discipline: re-running setup must not create duplicate role grants, since Spatie's underlying pivot table has a unique constraint on (model, role) but the action itself should not rely on a caught exception for control flow. [Source: prd.md#FR-005] [Inference]
- **Async work boundary**: ADR-005 names `SendSchedaEmail`, `GenerateSchedaPdf`, `SyncSigmaEmployees`, `ReconcileSigmaRecords`, `ArchiveActivityLogs` as the queued-job set; role assignment is not in that list, so this action runs synchronously within the Filament request (small batch sizes expected: invite batches, not full-tenant re-permissioning). [Source: architecture.md#adr-005] [Inference]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test types**: unit tests for `AssignRolesToInviteBatchAction` (`preview()` and `commit()` separately); feature test asserting the Activity trail and Spatie role pivot after a full confirm flow.
- **AC #1/#2**: seed an invite batch with a mix of valid role strings (`staff`, `evaluator`) and an invalid one (`superuser`); call `preview()`; assert the valid rows are marked assignable, the invalid row is marked unrecognized, and no `model_has_roles` pivot rows exist yet.
- **AC #3**: call `commit()` on a validated batch; assert each user now `hasRole()` the correct role; call `commit()` a second time on the same batch and assert the pivot row count for each user does not increase (idempotency).
- **AC #4**: create invite batches in two tenants; commit tenant A's batch; assert tenant B's invited users remain unassigned.
- **AC #5**: after `commit()`, assert one `Activity` row per successfully assigned user with `action = 'role_change'`, correct `model_id`/`user_id`, and the confirming admin as actor.
- **Fixtures**: reuse `User`/`Tenant` factories from 6.1/6.2; seed roles via `RoleSeeder` (6.1) in test setup rather than re-implementing role creation.
- **Edge cases**: empty invite batch (no-op, no error), all-unrecognized batch (preview report is entirely "unrecognized", commit is a no-op), a user whose intended role changed between preview and commit (re-validate at commit time, do not trust a stale preview).
- Do not execute tests, linters, or builds as part of this planning story: this section defines the strategy only.
