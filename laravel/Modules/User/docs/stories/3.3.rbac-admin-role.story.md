# 3.3: RBAC: Admin role (all CRUD, user mgmt)

**Story ID:** 3.3
**Epic:** 3: Access Control & Security
**Slug:** rbac-admin-role
**Status:** backlog

## Story

As a PA admin,
I want full CRUD access to Scheda records and the ability to manage users and role assignments,
so that I can administer my PA's tenant end-to-end without needing database access.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. `pa_admin` role is granted full CRUD on Scheda: `SchedaPolicy::create()`, `::update()`, `::delete()`, `::restore()` all return `true` for `pa_admin`. [Source: prd.md#FR-005: "pa_admin (all access)"]
2. `Modules/User/app/Filament/Resources/UserResource.php` exists, letting `pa_admin` create/edit users and assign one or more of the 5 seeded roles via a dropdown/select; gated by a new `Modules/User/app/Policies/UserPolicy.php`. [Source: prd.md: Epic 3 Story 3.1 narrative: "Assign user to role via dropdown + save"]
3. `hr_admin` and `finance` role permissions are confirmed present in the seeded permission matrix from 3.1: `hr_admin` has Sigma CRUD permission, `finance` has reports-read-only permission: verified by policy assertions (Sigma/Performance resource implementation itself is out of scope for Epic 3). [Source: prd.md: Epic 3 Story 3.1 narrative: "Matrix: staff [read own Scheda], evaluator [CRUD own dept Scheda], hr_admin [CRUD Sigma], finance [read reports only]"; Source: prd.md#FR-005]
4. `UserResource` is inaccessible (nav-hidden and policy-denied) to any role other than `pa_admin`. [Source: prd.md#NFR-SEC-003: "Enforce: Spatie Permissions middleware on every Filament resource"]
5. Role+action matrix test proves: `pa_admin` passes every Scheda policy check and every `UserPolicy` check; `evaluator`/`staff`/`finance`/`hr_admin` are all denied `UserPolicy` access. [Source: prd.md#FR-005: "Test: 100% coverage of role+action combos"; Source: prd.md#NFR-SEC-003: "Test: 100% coverage (every role tested on every action)"]

## Tasks / Subtasks

- [ ] Add `delete()`/`restore()` methods to `Modules/User/app/Policies/SchedaPolicy.php`, granting `pa_admin` (AC: #1)
- [ ] Create `Modules/User/app/Filament/Resources/UserResource.php` with form fields for name/email and a multi-select for the 5 seeded Spatie roles (AC: #2)
- [ ] Create `Modules/User/app/Policies/UserPolicy.php` restricting all actions (`viewAny`, `view`, `create`, `update`, `delete`) to `pa_admin` (AC: #2, #4)
- [ ] Assert `hr_admin` has Sigma-CRUD-equivalent permission strings and `finance` has reports-read-only permission strings in the 3.1 seed matrix (no new UI, assertion only) (AC: #3)
- [ ] Hide `UserResource` from Filament navigation for non-`pa_admin` roles via `shouldRegisterNavigation()` gate (AC: #4)
- [ ] Write role+action matrix test covering `pa_admin` on Scheda CRUD + UserResource, and negative cases for all other roles on `UserPolicy` (AC: #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Architecture component:** Access Control (`User`, `Tenant`): "Auth, roles, permissions, tenant policy" via "Laravel auth, Spatie roles, policies, RLS policies." [Source: architecture.md#component-design: Access Control row]
- **Filament as the admin contract:** ADR-002 establishes Filament resources for operational CRUD (evaluators, HR, finance, PA admins); staff stay on the thin Blade portal (3.6). `UserResource` is exactly this kind of admin workflow. [Source: architecture.md#adr-002: "Build administrative workflows in Filament resources... Filament remains the admin contract"]
- **FR-005 role list is authoritative:** `staff`, `evaluator`, `hr_admin`, `finance`, `pa_admin`, with `pa_admin` holding "all access." [Source: prd.md#FR-005]
- **Data model:** `User` row carries `tenant_id`, `email`, `name`, `sigma_employee_id`, with roles attached via Spatie. [Source: architecture.md#data-model: `User` row]
- **NFR-SEC-003 enforcement point:** "Enforce: Spatie Permissions middleware on every Filament resource + API endpoint": this is the concrete mechanism `UserResource`'s policy gate must satisfy. [Source: prd.md#NFR-SEC-003]
- **Scope boundary:** implementing the actual Sigma CRUD UI (`Modules/Sigma/app/Filament/Resources/SigmaResource.php`) and the Performance/reports UI is Epic 2 and Epic 1(.3) scope respectively: this story only confirms the `hr_admin`/`finance` permission ROWS exist in the shared seed matrix, it does not build those resources. [Inference, based on sharding-context.md Epic 2/Epic 1 file ownership excluding Epic 3.]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature/policy tests (Pest); one Filament resource smoke test (page loads for `pa_admin`, 403/hidden for others) if a Filament testing harness is already configured in the repo: otherwise policy-level assertions are sufficient for this story's sizing.
- **Fixtures:** `User` factory with each of the 5 roles; a target `User` fixture to be edited/role-reassigned via `UserResource`.
- **Scenarios to prove each AC:**
  - AC #1: `pa_admin` user passes `create`/`update`/`delete`/`restore` on `SchedaPolicy`.
  - AC #2: `pa_admin` can save a `UserResource` form assigning a new role to a target user; role persists via Spatie `hasRole()`.
  - AC #3: assert `hr_admin` and `finance` permission sets contain the expected Sigma/reports permission strings from the 3.1 seed.
  - AC #4: non-`pa_admin` roles denied `UserPolicy::viewAny()`; navigation item absent for those roles.
  - AC #5: full role/action matrix table test: `pa_admin` row only for new assertions (evaluator/staff rows already covered in 3.1/3.2, do not duplicate).
- **Edge cases:** `pa_admin` attempting to remove their own `pa_admin` role (should be allowed by policy but flagged as a UX/business-rule concern for the dev agent, not blocked by this story's ACs); user with zero roles assigned after a bad save (policy must not silently grant default access).
