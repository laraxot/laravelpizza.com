# Story 11.2: rate limiting sul login

## Contesto (audit BMAD "perfezione assoluta", 2026-09-22)

`grep -rn "throttle"` in tutto `Modules/User` restituisce un solo risultato,
dentro `laravel/Modules/User/routes/auth.php`: il cui intero contenuto (righe
4-26) e' avvolto in un blocco di commento (`/* ... */`), quindi morto/inattivo.
`grep -rn "RateLimiter::\|tooManyAttempts\|hit("` in `app/` → 0 risultati.
`LoginWidget.php`/`BaseAuthWidget.php` (i componenti Filament che gestiscono
davvero il login, essendo `routes/auth.php` disattivo) non contengono
`HasRateLimitedForms` ne' logica di throttling propria.

**Impatto:** nessuna protezione contro tentativi di login ripetuti (brute-force,
credential stuffing) sul form di login reale.

## User story

Come proprietario del sistema,
voglio che il login sia protetto da tentativi ripetuti,
cosi' che un attaccante non possa provare password in loop illimitato.

## Acceptance criteria

- [ ] `LoginWidget` (o la sua base Filament) applica un rate limit reale per
      tentativo di login: pattern standard Filament (`HasRateLimitedForms`) o
      `RateLimiter::attempt()`/`tooManyAttempts()` espliciti.
- [ ] Il limite e' per combinazione IP+identificativo (non solo IP, per non
      bloccare un intero ufficio dietro NAT; non solo email, per non permettere
      lo user enumeration di username validi tramite messaggi diversi).
- [ ] Dopo N tentativi falliti (soglia da definire in implementazione, standard
      Filament e' ragionevole default), il form mostra un messaggio di attesa e
      rifiuta ulteriori tentativi fino a decadenza del lock.
- [ ] Nessuna regressione sul flusso di login legittimo (utente con password
      corretta al primo tentativo non e' mai bloccato).
- [ ] Se `routes/auth.php` resta permanentemente disattivo (Livewire retirato,
      vedi Epic 10), il blocco di codice commentato va rimosso o marcato
      esplicitamente come riferimento storico, non lasciato come falso segnale
      di protezione esistente.
- [ ] Test che verifica il blocco dopo N tentativi falliti e lo sblocco dopo il
      periodo di decadenza (Pest, con `Carbon::setTestNow` per simulare il
      tempo, non un vero `sleep`).

## Piano di verifica

1. Test Pest: loop di tentativi falliti oltre soglia → assert risposta di blocco
   (status/redirect/messaggio, secondo l'implementazione scelta).
2. Verifica manuale/automatica che un tentativo legittimo dopo il periodo di
   decadenza torni a funzionare.
