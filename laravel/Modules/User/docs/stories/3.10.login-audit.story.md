# 3.10: Login audit: log all auth events

**Story ID:** 3.10
**Epic:** 3: Access Control & Security
**Slug:** login-audit
**Status:** backlog

## Story

As a PA admin,
I want every authentication event (login success, login failure, logout) recorded in the audit log,
so that suspicious access patterns can be investigated and the PA can demonstrate GDPR-required audit coverage of access to personal data.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A successful login by any user (Filament or staff portal) creates an Activity log entry recording the user, action (`login`), IP address, and timestamp. [Source: prd.md#FR-006: "Triggered by: ...user login (optional)"; Source: prd.md#NFR-SEC-001: "Audit: Activity log tracks all access to staff personal data"]
2. A failed login attempt creates an Activity log entry recording the attempted identifier (email), action (`login_failed`), IP address, and timestamp, without recording the attempted password or other credential material. [Source: prd.md#NFR-SEC-001: GDPR data-minimization principle applied to audit logging itself]
3. A logout creates an Activity log entry recording the user, action (`logout`), and timestamp. [Source: prd.md#FR-006: Activity log columns include action/timestamp per event]
4. Login/logout event logging does not block or measurably delay the authentication flow: it is dispatched as a non-blocking listener, not inline in the critical auth path. [Source: architecture.md#component-design: "Audit/GDPR (`Activity`) | ... | Domain event subscribers, export controller, archive job"]
5. Login audit entries are queryable per-tenant and per-user, consistent with the same `tenant_id`/`user_id` scoping used by the rest of the Activity log. [Source: architecture.md#data-model: `Activity` row: `id`, `tenant_id`, `user_id`, `action`, `model_type`, `model_id`, `old_value`, `new_value`, `ip_address`, `created_at`]

## Tasks / Subtasks

- [ ] Register Laravel auth event listeners (`Illuminate\Auth\Events\Login`, `Failed`, `Logout`) in `Modules/User/app/Providers/EventServiceProvider.php` (or the module's existing event service provider if one exists) (AC: #1, #2, #3)
- [ ] Implement listener classes that call into the Epic 4-owned `Activity` logging mechanism (e.g., `Activity::log(...)` or equivalent, external contract) rather than writing directly to the `Activity` table's schema (AC: #1, #2, #3, #5)
- [ ] Ensure the `Failed` event listener captures only the attempted email/identifier and IP, explicitly excluding password/credential fields from the logged payload (AC: #2)
- [ ] Dispatch listeners via Laravel's queued-listener mechanism (`ShouldQueue`) so auth flow latency is unaffected (AC: #4)
- [ ] Write feature tests simulating login success, login failure, and logout, asserting the correct Activity entries are created (or the correct external call is made, per Epic 4's contract) (AC: #1, #2, #3, #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Cross-epic dependency flagged:** the `Activity` model and its append-only logging mechanism belong to Epic 4's file scope (`Modules/Activity/app/Models/Activity.php`), per both the component-design table and sharding-context.md's explicit Epic 4 ownership list. [Source: architecture.md#component-design: "Audit/GDPR (`Activity`) | Append-only activity log, retention, GDPR export | Domain event subscribers, export controller, archive job"] `[Inference]` This story therefore implements only the LISTENER side (subscribing to Laravel's built-in auth events and forwarding them to Epic 4's logging contract) within `Modules/User`; it does not create or modify `Modules/Activity/app/Models/Activity.php`. If Epic 4's `Activity::log()`-style helper does not yet exist at implementation time, the dev agent should raise a cross-epic blocker (mirrors 3.7's same dependency pattern) rather than writing directly to the `activity` table's schema from within `Modules/User`.
- **FR-006 explicitly names login as an optional trigger:** "Triggered by: Scheda model events..., user login (optional)." [Source: prd.md#FR-006] This story treats that "(optional)" trigger as REQUIRED, because NFR-SEC-001 independently mandates auditing "all access to staff personal data," and login is the entry point to that access. [Source: prd.md#NFR-SEC-001] `[Inference]` Resolving the "(optional)" qualifier in FR-006 against NFR-SEC-001's stronger mandate in favor of implementing it; flagged here so the dev agent understands this is a synthesis, not a verbatim requirement.
- **Data-minimization in the failed-login case:** GDPR data minimization is a named principle under NFR-SEC-001 ("data minimization, consent"). [Source: prd.md#NFR-SEC-001] `[Inference]` Applying that general principle specifically to AC #2's exclusion of password data from failed-login logs: not a verbatim PRD statement about login logging specifically, but a direct application of the cited principle to this event type (logging a raw password attempt would itself be a data-protection violation).
- **Non-blocking dispatch rationale:** the architecture's Audit/GDPR component lists "Domain event subscribers" as its integration mechanism. [Source: architecture.md#component-design] `[Inference]` "Domain event subscribers" implies an async/decoupled listener pattern (Laravel's `ShouldQueue` listeners) rather than inline synchronous logging within the login controller: chosen to avoid coupling auth-flow performance/availability to the audit subsystem's health, consistent with standard Laravel event-listener practice.
- **`EventServiceProvider.php` may be a new or existing file:** `[Inference]` if `Modules/User` does not yet have an `app/Providers/EventServiceProvider.php`, this story creates it; if one already exists (e.g., from an earlier, unlisted setup story), this story adds registrations to it. The dev agent should check for an existing provider before creating a new one.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest) using Laravel's auth event testing helpers (`Event::fake()` for dispatch verification, and a full login flow test for end-to-end confirmation).
- **Fixtures:** `User` factory (any role); valid and invalid credential pairs for login success/failure cases.
- **Scenarios to prove each AC:**
  - AC #1: successful login via the standard auth flow results in a `login` Activity entry (or the expected call to Epic 4's logging contract) with correct user/IP/timestamp.
  - AC #2: failed login attempt results in a `login_failed` entry with the attempted email and IP, and explicit assertion that no password/credential string appears anywhere in the logged payload.
  - AC #3: logout results in a `logout` entry.
  - AC #4: listener is registered as `ShouldQueue` (or dispatched via `Bus::dispatch`/queue): assert via reflection/queue-fake that the listener does not run synchronously inline with the HTTP response, or assert queue push occurred via `Queue::fake()`.
  - AC #5: entries carry the correct `tenant_id` (per 3.5's scope) and `user_id`.
- **Edge cases:** login attempt for a user that doesn't exist at all (failed-login log should still record the attempted email without erroring on a missing user relation); concurrent login attempts from the same IP (should not deduplicate or drop entries); logout when no authenticated session exists (should be a no-op, not an error).
