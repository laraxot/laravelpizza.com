# 4.1: Activity log: immutable event stream (creation, edit, approval, email sent)

**Story ID:** 4.1
**Epic:** 4 — Audit & Compliance
**Slug:** immutable-activity-log
**Status:** backlog

## Story

As a PA compliance officer,
I want every Scheda creation, edit, approval, and email-sent action recorded as an immutable Activity entry,
so that the PA has a complete, tamper-proof audit trail for D.Lgs. 165/2001 and GDPR evidence.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. An Activity entry is created for each of: Scheda create, Scheda update, Scheda soft-delete, ProgressioniApproval approve, and Scheda email-sent, capturing actor (`user_id`/causer), action type, subject (`model_type`/`model_id`), old/new value diff, timestamp, and IP address. [Source: prd.md#FR-006 — "Columns: id, user_id, action (create/update/approve/email/role_change), model_type, model_id, old_value, new_value, timestamp, ip_address"; "Triggered by: Scheda model events (created/updated/soft-deleted), ProgressioniApproval events, user login (optional)"]
2. Approval and email-sent events are logged — these two event types are not covered by the module's current listeners (only `Login`/`Logout` are wired) and have no existing logging Action (`LogModelCreatedAction`/`LogModelUpdatedAction`/`LogModelDeletedAction` exist; no approval or email-sent equivalent exists yet). [Source: prd.md#FR-006] [Inference — gap confirmed by reading `Modules/Activity/app/Providers/EventServiceProvider.php` (Login/Logout only) and the `Modules/Activity/app/Actions/` directory (no `LogModelApprovedAction`/`LogEmailSentAction`)]
3. Each Activity entry stores the source IP address of the actor; this is a new capability — the current `Activity` model's `$fillable` list (`id, log_name, description, subject_type, event, subject_id, causer_type, causer_id, properties, attribute_changes, batch_uuid`) has no `ip_address` column. [Source: prd.md#FR-006] [Inference — confirmed by reading `Modules/Activity/app/Models/Activity.php`]
4. Activity rows are append-only: no application code path updates or hard-deletes an Activity row, except a legally required erasure workflow that writes a redaction marker instead of deleting the row. [Source: architecture.md#adr-009 — "Activity rows are append-only except legally required erasure workflows, which write a redaction marker."]
5. Activity entries are filterable in the Filament `ActivityResource` by date range, actor (user), action type, and subject model type. [Source: prd.md#FR-006 — "Queryable: filter by date range, user, action, model"]

## Tasks / Subtasks

- [ ] Add `ip_address` as a fillable/cast column on `Modules/Activity/app/Models/Activity.php` and a matching additive migration guarded by `hasColumn()` (no drops, per sacred-data migration policy) (AC: #3)
- [ ] Create `Modules/Activity/app/Actions/LogModelApprovedAction.php` and a corresponding listener wired for `ProgressioniApproval` approve events, mirroring the existing `LogModelCreatedAction` → `LogActivityAction` delegation pattern (AC: #1, #2)
- [ ] Create `Modules/Activity/app/Actions/LogEmailSentAction.php` and a corresponding listener wired for the Scheda email-sent event (consumed from Epic 1's Notify module event, external dependency — do not modify `Modules/Notify`) (AC: #1, #2)
- [ ] Register the new approval and email-sent listeners in `Modules/Activity/app/Providers/EventServiceProvider.php`, additive only — preserve the existing `Login`/`Logout` registrations (AC: #1, #2)
- [ ] Capture the actor's IP address (`request()->ip()`) in the shared `LogActivityAction` (or equivalent) so every logging path populates it, not just the two new ones (AC: #1, #3)
- [ ] Add a model-level guard on `Activity` (e.g. override `update()`/`delete()` to throw unless a redaction-marker flag is set) enforcing append-only behavior (AC: #4)
- [ ] Extend `Modules/Activity/app/Filament/Resources/ActivityResource.php`'s table with filters for date range, `causer_id`, `event`, and `subject_type` (AC: #5)
- [ ] Write feature tests proving each of the five triggering events produces a correctly populated, immutable Activity row (AC: #1-#5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **FR-006 full acceptance criteria**: "Columns: id, user_id, action (create/update/approve/email/role_change), model_type, model_id, old_value, new_value, timestamp, ip_address"; "Triggered by: Scheda model events (created/updated/soft-deleted), ProgressioniApproval events, user login (optional)"; "Queryable: filter by date range, user, action, model"; "Retention: 7-year archive policy (auto-move to cold storage after 2 years)" (owned by story 4.2, not this one); "GDPR: staff can export own activity" (owned by Epic 3 story 3.7, not this one). [Source: prd.md#FR-006]
- **ADR-009 grounding**: "Create Activity entries from domain events for create/update/delete/approve/email/export/role-change/sync actions. Activity rows are append-only except legally required erasure workflows, which write a redaction marker." "Stories that mutate Scheda, roles, Sigma state, or exports must emit Activity events." [Source: architecture.md#adr-009]
- **Existing schema already satisfies old/new value capture**: the current `Activity` model casts `properties` to `SchemalessAttributes` and `attribute_changes` to `collection` — this is Spatie Activitylog's standard mechanism for storing before/after diffs, so `old_value`/`new_value` from FR-006 map onto these existing JSON columns rather than requiring new dedicated columns. [Inference — confirmed by reading `Modules/Activity/app/Models/Activity.php` casts()]
- **`ip_address` is the one genuine schema gap**: not present in `$fillable` or the model's PHPDoc property list. [Inference — confirmed by reading `Modules/Activity/app/Models/Activity.php`]
- **Existing logging Action pattern to extend, not replace**: `LogModelCreatedAction` (and its siblings `LogModelUpdatedAction`, `LogModelDeletedAction`) delegate to a shared `LogActivityAction`; `LogUserLoginAction`/`LogUserLogoutAction` follow the same shape. New approval/email-sent Actions should follow this exact delegation pattern for consistency. [Inference — confirmed by reading `Modules/Activity/app/Actions/LogModelCreatedAction.php`]
- **Redaction mechanism already exists**: `Modules/Activity/app/Actions/RedactModelAttributesAction.php` strips `password`, `remember_token`, `two_factor_secret`, `two_factor_recovery_codes` before persisting to the log — this is the existing carve-out mechanism ADR-009 refers to as "legally required erasure workflows... write a redaction marker"; this story's append-only guard (task 6) must not block this action's legitimate write path. [Inference]
- **Component design**: "Audit/GDPR (`Activity`) | Append-only activity log, retention, GDPR export | Domain event subscribers, export controller, archive job | Activity entries, export files, archive pointers | ADR-005, ADR-009, ADR-010". [Source: architecture.md#component-design]
- **Data model**: `Activity` entity — `id, tenant_id, user_id, action, model_type, model_id, old_value, new_value, ip_address, created_at`; "append-only; archive after 2 years"; indexed on `tenant_id, user_id, model_type, model_id, created_at`. [Source: architecture.md#data-model]
- **Coverage matrix**: FR-006 → component "Audit/GDPR", ADRs "ADR-003, ADR-009", status "Addressed". [Source: architecture.md#fr-nfr-coverage-matrix]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest) hitting the real event/listener chain (dispatch a `ProgressioniApproval` approve event, an email-sent event, Scheda create/update/soft-delete) and asserting the resulting `Activity` row shape; one unit test on the model-level append-only guard.
- **Fixtures:** `Scheda` factory (Epic 1 scope — use if available, else a minimal stub model with `LogsActivity`), `ProgressioniApproval` factory, `User` factory as actor, a fake/mock email-sent event.
- **Scenarios to prove each AC:**
  - AC #1: for each of the five trigger types, assert exactly one Activity row exists with `causer_id`, `event`, `subject_type`, `subject_id`, `created_at`, and `ip_address` populated.
  - AC #2: assert an approval event and an email-sent event each produce an Activity row (regression test against the confirmed gap — these produced zero rows before this story).
  - AC #3: assert `ip_address` is non-null and matches the request IP used in the test's `withServerVariables(['REMOTE_ADDR' => ...])`.
  - AC #4: attempt to call `update()` and `delete()` directly on an `Activity` model instance outside the redaction path and assert an exception/guard is raised; assert `RedactModelAttributesAction`'s write path still succeeds.
  - AC #5: assert `ActivityResource`'s table query, when filtered by date range/user/action/model type, returns only matching rows.
- **Edge cases:** event dispatched with no authenticated actor (system/queue context) — `causer_id` should be nullable, not crash; rapid duplicate events (e.g. double-submit) should not silently merge or overwrite an existing row (each dispatch is a new append).
