# 3.7: GDPR export: personal data (JSON/CSV, <30 days)

**Story ID:** 3.7
**Epic:** 3 — Access Control & Security
**Slug:** gdpr-export
**Status:** backlog

## Story

As a staff member,
I want to download my own personal data (Scheda records and activity mentioning me) in a machine-readable format,
so that I can exercise my GDPR Article 20 right to data portability without waiting on a manual PA data request.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. The staff portal (3.6) exposes a "Download my data" action that triggers an export request scoped to the authenticated staff member's own Scheda records and Activity entries mentioning them. [Source: prd.md#FR-008 — "Trigger: Download my data button"; "Scope: own Scheda + activity mentioning that staff member"]
2. The export is produced in JSON format including metadata (`export_date`, `data_retention_policy`); a CSV variant is also offered per NFR-REG-002's machine-readable requirement. [Source: prd.md#FR-008 — "Format: JSON with metadata (export_date, data_retention_policy)"; Source: prd.md#NFR-REG-002 — "Export format: JSON/CSV machine-readable (not just PDF)"]
3. The export completes and is available for download within 5 minutes of the request (target), and in all cases within the 30-day statutory maximum. [Source: prd.md#FR-008 — "Timeliness: <5 minutes"; Source: prd.md#NFR-REG-002 — "Timeliness: <30 days (target 5 minutes via FR-008)"]
4. The export excludes HR-internal notes and internal flags, containing only the staff member's own personal data. [Source: prd.md#NFR-REG-002 — "Completeness: personal data only (exclude HR notes, internal flags)"]
5. Every export request and download is recorded so the access is auditable, consistent with GDPR's audit requirement for personal-data access. [Source: prd.md#NFR-SEC-001 — "Audit: Activity log tracks all access to staff personal data"]
6. The export route enforces the same policy and tenant scoping as the rest of the staff portal — a staff member cannot request another employee's export by manipulating the request. [Source: architecture.md#api-specifications — "GDPR export request/download. Auth: staff policy plus tenant/RLS."]

## Tasks / Subtasks

- [ ] Add a `download`/`export` route and controller action in `Modules/Activity/app/Http/Controllers/GdprExportController.php`, triggering an export scoped to `auth()->user()`'s own Scheda + mentions in Activity (AC: #1, #6)
- [ ] Build the export payload assembler producing JSON (with `export_date`, `data_retention_policy` metadata) and CSV variants, excluding HR-internal fields (AC: #2, #4)
- [ ] Wire export generation to complete synchronously if fast enough, or via a queued job with a status-check/download-when-ready flow, targeting <5 minutes (AC: #3)
- [ ] Ensure the export request and resulting download are each logged as Activity entries through the Activity module contract (AC: #5)
- [ ] Add a policy check (reusing 3.2's `SchedaPolicy` scoping and 3.5's tenant scope) before assembling the export (AC: #6)
- [ ] Write a feature test proving export content, format, exclusion of internal fields, and cross-employee denial (AC: #1-#6)

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest); one test verifying JSON schema/content shape, one verifying CSV output, one verifying cross-employee denial.
- **Fixtures:** `User` factory (staff role, tenant-scoped) with associated `Scheda` and `Activity` records (Epic 1/Epic 4 factories, or minimal stubs if those epics haven't landed); a second employee's records to prove exclusion.
- **Scenarios to prove each AC:**
  - AC #1/#6: staff user triggers export, receives only their own data; a second staff user cannot trigger or access the first user's export artifact (authorization + ownership check on the download link/token).
  - AC #2: assert JSON payload includes `export_date` and `data_retention_policy` keys; assert a CSV variant is downloadable and parses to the same underlying rows.
  - AC #3: assert export completes (job dispatched and processed, or synchronous response) within the test's simulated time budget; do not assert wall-clock timing in a unit test — assert the mechanism (queued vs synchronous) matches the <5 minute design intent.
  - AC #4: assert HR-internal fields (e.g., internal flags, HR notes columns) are absent from the payload even when present in the underlying Scheda record.
  - AC #5: assert an `Activity` entry (or equivalent Epic-4-provided call) is recorded for both the export request and the download event.
- **Edge cases:** staff user with no Scheda/Activity records (export still succeeds, empty arrays, not an error); repeated export requests in quick succession (should not error or duplicate-log unboundedly — flag rate-limiting as a follow-up concern if not already covered by NFR-SEC-* elsewhere, do not implement here).
