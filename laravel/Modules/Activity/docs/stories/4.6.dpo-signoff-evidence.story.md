# 4.6: GDPR DPO sign-off: impact assessment + evidence

**Story ID:** 4.6
**Epic:** 4 — Audit & Compliance
**Slug:** dpo-signoff-evidence
**Status:** backlog

## Story

As a PA Data Protection Officer,
I want a recorded GDPR compliance checklist and impact-assessment sign-off, backed by links to the audit evidence produced elsewhere in Epic 4,
so that the PA can prove pre-launch GDPR compliance review before going to production.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A `DpoSignOff` record captures the checklist items reviewed, the reviewing DPO's identity, the sign-off decision (approved/rejected/pending), a decision timestamp, and free-text notes. [Source: prd.md#NFR-SEC-001 — "DPO review: GDPR compliance checklist signed off by PA DPO before production"] [Source: prd.md#NFR-REG-002 — "DPO review: GDPR impact assessment signed off before launch"] [Inference — record shape synthesized from the requirement text; prd.md/architecture.md do not publish an explicit DpoSignOff schema]
2. The checklist references, by link or ID, the concrete evidence already produced by this epic: the immutable Activity log (4.1), the retention/archive job (4.2), and appeal logging (4.3) — so the DPO's decision is traceable to specific implemented controls, not a free-standing form. [Source: prd.md#NFR-SEC-001] [Source: prd.md#NFR-REG-002] [Inference — traceability linkage synthesized from the epic's own dependency structure]
3. Only a user with a DPO-equivalent role can create or update a sign-off decision; all other roles (including admin) can view but not edit it, distinct from the existing RBAC roles already defined for the project. [Source: prd.md#NFR-SEC-001] [Inference — role restriction synthesized from the requirement's compliance-gate intent]
4. Every sign-off creation and status change emits an Activity log entry, consistent with this epic's own append-only audit discipline. [Source: architecture.md#adr-009 — "Stories that mutate Scheda, roles, Sigma state, or exports must emit Activity events."]
5. A Filament resource lets the DPO view the checklist, attach notes, and record the decision; the resource is read-only for non-DPO roles. [Source: prd.md#NFR-SEC-001] [Inference — UI surface synthesized from the requirement's review-workflow intent]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Feature tests (Pest) covering sign-off creation, role-restricted editing, Activity emission, and evidence-link correctness; one policy test for non-DPO write denial.
- **Fixtures:** `User` factory with a DPO-equivalent role/permission assigned; `User` factory with admin/HR role (for the negative access-control case); seeded Activity, archive-job, and appeal records (or minimal stubs referencing 4.1/4.2/4.3's factories) to populate evidence links.
- **Scenarios to prove each AC:**
  - AC #1: creating a sign-off record populates checklist items, reviewer identity, decision, `decided_at`, and notes.
  - AC #2: assert the sign-off record's evidence links resolve to real Activity/archive/appeal records (or their IDs), not placeholder text.
  - AC #3: a DPO-role user can create/update a sign-off; an admin or staff user attempting to do so is denied (403/policy exception); all roles can view an existing sign-off.
  - AC #4: assert exactly one Activity entry is produced on sign-off creation and one on each decision change.
  - AC #5: a DPO-role user can access `DpoSignOffResource`'s edit form; a non-DPO role sees a read-only view (no save action available).
- **Edge cases:** a sign-off attempted before 4.1/4.2/4.3's evidence exists (empty tenant with no Activity/archive/appeal records yet) — should still allow record creation but show "no evidence available yet" rather than erroring; a second sign-off submitted after a prior "approved" decision (should be recorded as a new decision entry reflecting the append-only discipline, not silently overwrite the prior approval).
