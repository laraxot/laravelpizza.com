# 6.4: Cleanup policy: soft-delete + archive scheduling

**Story ID:** 6.4
**Epic:** 6 — Setup & Operations
**Slug:** cleanup-policy-archive-scheduling
**Status:** backlog

## Story

As a PA admin completing tenant setup,
I want the archive/cleanup schedule and retention defaults registered automatically,
so that Activity logs age out to cold storage on schedule without a manual cron step per PA.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A scheduled task registers the existing Activity auto-archive job (delivered under Epic 4, e.g. `ArchiveActivityLogs`/`ArchiveActivity`) to run weekly during off-peak hours for each tenant provisioned via the setup wizard. [Source: prd.md#NFR-OP-003] [Source: architecture.md#adr-005]
2. A Setup-module artisan command verifies the archive schedule is registered and reports its next scheduled run time, usable as a setup-completion checklist item. [Source: prd.md#NFR-OP-003]
3. Retention defaults — archive after 2 years, hard-delete after 7 years — are stored in Setup-module config and are the values a newly provisioned tenant is set up with; this story only schedules/configures, it never performs a destructive delete itself. [Source: prd.md#NFR-OP-003] [Source: architecture.md#adr-009]
4. The setup command confirms that `Scheda` (and any other model the wizard registers as soft-deletable) uses the `SoftDeletes` trait, and fails the checklist item if it does not. [Source: architecture.md#data-model]
5. Scheduling changes are additive only: existing entries in the shared scheduler registration file are preserved; this story appends the archive-run and verification-command entries without removing or reordering existing schedule entries. [Inference: forward-only change discipline applied to a shared file]

## Tasks / Subtasks

- [ ] Add Setup-module `config/setup.php` with `archive_after_years = 2` and `hard_delete_after_years = 7` defaults (AC: #3)
- [ ] Register the weekly off-peak schedule entry for the existing Activity archive job in the shared scheduler file, additive-only (AC: #1, #5)
- [ ] Implement `VerifyCleanupPolicyCommand` (artisan) that inspects the schedule and prints the next run time for the archive job (AC: #2)
- [ ] Extend `VerifyCleanupPolicyCommand` (or a small `SoftDeletePolicyCheckAction`) to reflect on `Scheda::class` (and any wizard-registered soft-deletable model list) and assert the `SoftDeletes` trait is present (AC: #4)
- [ ] Wire the command's pass/fail result into the Setup wizard's completion checklist output (AC: #2, #4)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Requirement numbering:** this story implements `NFR-OP-003: MUST — Activity Log Auto-Archive`; do not introduce any new NFR ID for archive scheduling. [Source: prd.md#NFR-OP-003]
- **NFR text**: "Policy: move records >2 years old to cold storage (S3 Glacier). Frequency: weekly cronjob (off-peak hours). Query redirect: searches on archive dates hit Glacier (slower, <2s SLA). Cleanup: hard-delete records >7 years per PA law (audit trail before deletion)." This is the literal source for the 2-year archive / 7-year hard-delete defaults and the weekly off-peak cadence. [Source: prd.md#NFR-OP-003]
- **Job already exists, this story only schedules it**: "Use Laravel queued jobs, scheduled commands, and retry/backoff policies for... `ArchiveActivityLogs`." The archive job itself is Epic 4's deliverable (`Modules/Activity/app/Jobs/ArchiveActivity.php` per sharding-context.md); this story's job is registering *when* it runs for a newly set-up tenant, not building the job. [Source: architecture.md#adr-005] [Source: sharding-context.md#epic-4]
- **Append-only / audit discipline**: "Activity rows are append-only except legally required erasure workflows, which write a redaction marker." The hard-delete-after-7-years config value must feed a process that still respects this — this story stores the config value only; it does not implement the deletion itself. [Source: architecture.md#adr-009]
- **Soft-delete constraint on Scheda**: data model table lists `Scheda` constraints as "score checks 1-10; year >= 2020; soft delete." The verification command in this story checks that this constraint is actually implemented in code (trait present) as a setup-time safety check, since a missing `SoftDeletes` trait would silently break the 30-day-restore behavior relied on elsewhere. [Source: architecture.md#data-model] [Inference: extending a data constraint into a setup-time verification step]
- **Deployment/ops constraint**: "Add 5-minute health checks, database backups with tested restore, CI validation for Git LFS pointers, and no US-based log shipping." Relevant context for where this story's scheduled command sits operationally, though health checks/backups/LFS are out of this story's scope (Epic 5/deployment infra). [Source: architecture.md#adr-010]
- **Shared-file caution**: the scheduler registration file (`routes/console.php` or an app-level `Kernel.php`, depending on Laravel version conventions already in the repo) is not owned exclusively by Epic 6 — other epics may register their own scheduled commands there. This story must add its entries without touching unrelated ones. [Inference]

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test types**: unit test for the schedule registration (assert the archive job appears in `Schedule::events()` with the expected weekly/off-peak cron expression); feature/console test for `VerifyCleanupPolicyCommand` output; unit test for the `SoftDeletes` trait reflection check.
- **AC #1**: inspect the application's `Schedule` container in a test and assert an entry exists whose command/job matches the Epic-4 archive job class, with a cron expression that falls in an off-peak window (e.g. not business hours) and a weekly frequency.
- **AC #2**: run `VerifyCleanupPolicyCommand` in isolation; assert exit code 0 and output containing a parseable "next run" timestamp when the schedule is registered; assert a non-zero exit code / clear failure message when it is not.
- **AC #3**: assert `config('setup.archive_after_years') === 2` and `config('setup.hard_delete_after_years') === 7` by default; assert these are read, not hardcoded, in the command output.
- **AC #4**: run the soft-delete check against `Scheda::class` (should pass, per architecture.md's documented constraint) and against a fixture/dummy model without the trait (should fail) to prove the check actually detects absence, not just presence.
- **AC #5**: diff the scheduler file's entries before/after this story's change in a test fixture; assert only additions, zero deletions or reorderings of pre-existing entries.
- **Fixtures**: a minimal dummy Eloquent model without `SoftDeletes` for the negative-case trait check; no real archive execution needed (archive job itself is out of scope — mock/spy it, don't run it against real data).
- **Edge cases**: schedule verification run before the wizard (6.1) has provisioned a tenant (should report "not yet scheduled," not throw); a tenant whose scheduled entry was manually removed outside this flow (verification command must detect and report absence, not assume success).
- Do not execute tests, linters, or builds as part of this planning story — this section defines the strategy only.
