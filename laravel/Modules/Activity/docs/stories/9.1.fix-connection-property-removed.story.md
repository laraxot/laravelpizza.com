# 9.1: Restore removed `$connection` from Activity models

**Story ID:** 9.1
**Epic:** 9 — Technical Debt / Corrections
**Slug:** fix-connection-property-removed
**Status:** done

## Story

As a developer,
I need the Activity log models to keep targeting the `activity` database connection,
so that audit events are correctly isolated from the main app connection and the existing
`Activity`, `Snapshot`, and `StoredEvent` queries keep working.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. The `$connection = 'activity'` property is present on `Modules/Activity/Models/Activity.php`,
   `Modules/Activity/Models/Snapshot.php`, and `Modules/Activity/Models/StoredEvent.php`.
2. After restoring the property, the existing Activity test suite passes and PSR-4 autoloading
   warnings for these classes no longer include "missing connection" related errors.
3. No other connection-related configuration (config files, `.env` keys) was modified by the
   removal — only the model property was touched.
4. A test asserts that model resolution uses the `activity` connection (i.e. the property is
   present and matches the configured connection name).

## Tasks / Subtasks

- [ ] Restore `protected $connection = 'activity';` on `Activity.php`
- [ ] Restore `protected $connection = 'activity';` on `Snapshot.php`
- [ ] Restore `protected $connection = 'activity';` on `StoredEvent.php`
- [ ] Run `php artisan test --filter Activity` to confirm green
- [ ] Add a small assertion (or extend existing tests) that the connection is `activity`

## Dev Notes

- **Root cause — analisi forense (2026-08-19):**
  Nel repo del modulo `laravel/Modules/Activity/` (`.git` separato dal monorepo),
  il commit `807b2f60` del **2026-03-06** (autore: Nicola `storgatonicola@provincia.treviso.it`)
  ha cambiato `protected $connection = 'activity'` → `protected $connection` (null implicito)
  in `Activity.php`. Il diff mostra che era un commit di pulizia docblock (rimozione spazi,
  `?mixed` → `mixed`) e la rimozione del valore era collaterale e probabilmente non intenzionale.
  Il commit successivo `873e2a73` (3 marzo) lo aveva già ripristinato; il commit `807b2f60`
  (6 marzo) lo ha rimosso di nuovo. La storia successiva ha ricreato il valore corretto.
  **Al 2026-08-19 i tre file hanno già `$connection = 'activity'` — il fix è applicato.**

- **Perché l'errore si ripete:** due repo git separati (monorepo radice + modulo Activity)
  rendono invisibili le modifiche al modulo in `git log` della radice. Un agente che lavora
  solo dalla radice non vede le modifiche al modulo e non può rilevare la rimozione.

- **Why it must stay:** `config/database.php` dichiara `activity` come connessione separata.
  I modelli devono dichiararla esplicitamente; senza, Eloquent usa la connessione default
  silenziosamente — i log finiscono nel DB sbagliato senza errori visibili.

- **Perché questo errore è grave:**
  Non c'è eccezione né log di errore quando la connessione cade sul default. Il bug è
  **silenzioso**: i log vengono scritti nel DB principale, corrompendo l'isolamento dei dati
  di audit. Può passare inosservato fino a quando qualcuno controlla le query sul DB sbagliato.

- **Source citations:**
  - `807b2f60` — commit che ha rimosso il valore (Nicola, 2026-03-06, repo modulo Activity)
  - `Modules/Activity/app/Models/Activity.php:113` — stato attuale corretto
  - `Modules/Activity/app/Models/Snapshot.php:46` — stato attuale corretto
  - `Modules/Activity/app/Models/StoredEvent.php:69` — stato attuale corretto

- **Rule learned (do NOT repeat):**
  > **Non rimuovere MAI `$connection` da un modello Eloquent** senza che ci sia una decisione
  > architetturale esplicita che sposta la tabella su un'altra connessione. L'assenza del valore
  > non è neutra: è un fallback silenzioso sulla connessione default che può rompere l'isolamento
  > dei dati senza errori visibili.

## Rule Update (Second Brain)

Add to edit-discipline rules:

> **Never remove a `$connection` override from an Eloquent model** unless the table has
> been migrated to a new connection. Connection overrides exist for a reason; the default
> connection is a fallback, not a safe replacement. Tag such removals as `risk:connection`.
