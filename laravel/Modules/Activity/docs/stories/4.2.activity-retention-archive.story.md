# 4.2: Activity retention: auto-archive >7 years

**Story ID:** 4.2
**Epic:** 4 — Audit & Compliance
**Slug:** activity-retention-archive
**Status:** backlog

## Story

As a PA compliance officer,
I want Activity log rows older than 2 years auto-moved to cold storage and rows older than 7 years hard-deleted with an audit trail,
so that the audit log stays performant and compliant with PA retention law without manual maintenance.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A queued job (`ArchiveActivity`) moves Activity rows older than 2 years to cold storage (S3 Glacier or equivalent object storage), run weekly during off-peak hours. [Source: prd.md#NFR-OP-003 — "Policy: move records >2 years old to cold storage (S3 Glacier). Frequency: weekly cronjob (off-peak hours)."] [Source: architecture.md#adr-005 — "Use Laravel queued jobs, scheduled commands, and retry/backoff policies for... `ArchiveActivityLogs`."]
2. Archived Activity data remains queryable: current-year query p95 latency stays <200ms, archive-year query p95 latency stays <2s. [Source: prd.md#NFR-REL-002 — "Query performance: <200ms for queries on current year; <2s on archive years"] [Source: prd.md#NFR-OP-003 — "Query redirect: searches on archive dates hit Glacier (slower, <2s SLA)"]
3. Activity rows older than 7 years are hard-deleted only after archival, and the deletion itself produces an audit trail entry (counts and date range removed) before the underlying rows are gone. [Source: prd.md#NFR-OP-003 — "Cleanup: hard-delete records >7 years per PA law (audit trail before deletion)"]
4. No Activity row is modified or deleted outside this job's 2-year archive step and 7-year cleanup step, and the GDPR redaction workflow (4.1's append-only guard) — this story does not reuse or extend the existing 90-day ad-hoc hard-delete in `ActivityMaintenanceAction`. [Source: architecture.md#adr-009 — "Activity rows are append-only except legally required erasure workflows, which write a redaction marker."] [Inference — conflict flag against `ActivityMaintenanceAction.php`'s existing 90-day chunked hard-delete, confirmed by reading that file]
5. Database growth stays bounded per the 5-year projection (100 PAs x 10k Scheda = 1M Scheda + 20M Activity entries) via indexing on `created_at`/`tenant_id`/`user_id` and the 2-year archive cutoff preventing hot-table bloat. [Source: prd.md#NFR-SC-002 — "Indexing: created_at, tenant_id, user_id for fast queries"; "Archival: Activity log cold-storage after 2 years prevents hot-table bloat."]

## Tasks / Subtasks

- [ ] Create `Modules/Activity/app/Jobs/ArchiveActivity.php` — dispatched weekly, off-peak — that selects Activity rows older than 2 years and moves them to object/cold storage (AC: #1)
- [ ] Create `Modules/Activity/app/Actions/ArchiveActivityBatchAction.php` (QueueableAction, matching module convention) performing the chunked move + row-count audit entry (AC: #1, #3)
- [ ] Implement archive-storage query redirection (or a documented fallback path) so archived rows remain queryable within the <2s SLA (AC: #2)
- [ ] Implement the 7-year hard-delete step, writing a summary Activity audit entry (row count, date range) immediately before the delete executes (AC: #3, #4)
- [ ] Confirm `created_at`, `tenant_id`, `user_id` indexes exist on the Activity table; add an additive migration if any are missing (AC: #5)
- [ ] Register the weekly off-peak schedule entry for `ArchiveActivity` (coordinate with 6.4, which also touches the shared scheduler registration file for tenant-level setup verification) (AC: #1)
- [ ] Write tests proving archive/hard-delete boundaries and confirming `ActivityMaintenanceAction` is not invoked by this job (AC: #1-#5)

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** Unit test for the job's row-selection boundary logic (2-year and 7-year cutoffs); feature test for the archive-then-delete sequence including the pre-delete audit entry; a scheduler-registration test verifying weekly/off-peak cadence.
- **Fixtures:** Activity rows factory-seeded at controlled ages (just under 2 years, just over 2 years, just under 7 years, just over 7 years) to test each boundary precisely.
- **Scenarios to prove each AC:**
  - AC #1: run the job against seeded rows; assert only rows older than 2 years are moved to cold storage, rows younger are untouched; assert the job is registered on a weekly, off-peak schedule.
  - AC #2: assert archived rows are still retrievable via the archive-aware query path (mock/fake the cold-storage backend in tests) and note the SLA target (<2s) as a design assertion, not a wall-clock timing test.
  - AC #3: assert a summary Activity audit entry (row count, date range) exists immediately before the 7-year-old rows are removed; assert no row of any age is hard-deleted without a preceding audit entry.
  - AC #4: assert `ActivityMaintenanceAction` is never invoked by `ArchiveActivity` or its Action (spy/mock it and assert zero calls); assert no Activity row modification occurs outside the two defined lifecycle transitions.
  - AC #5: assert `created_at`, `tenant_id`, `user_id` indexes exist on the Activity table (schema introspection test).
- **Edge cases:** a PA/tenant with zero Activity rows older than 2 years (job runs, no-op, no error); a row exactly at the 2-year or 7-year boundary (use a explicit, documented inclusive/exclusive boundary rule and test it); job re-run idempotency (running the archive job twice on the same data must not double-archive or double-delete).
