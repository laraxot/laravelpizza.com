# Tenant: unique/exists sui modelli Sushi (connessione per nome)

Fase BMAD: implementazione e verifica di un bugfix; l'integrazione finale in `SushiToJson` attende una decisione (#19).

## Sintomo

`/sigma/admin/web-services/create`, form con `TextInput::make('name')->unique(ignoreRecord: true)` su `Modules\Sigma\Models\WebService`:

`no such table: web_services (Connection: Modules\Sigma\Models\WebService, Database: :memory:, SQL: select count(*) ... where "name" = ttt)`

## Causa (verificata sul codice, riprodotta con test rossi)

1. `Sushi::getConnectionName()` restituisce `static::class` (`vendor/calebporzio/sushi/src/Sushi.php:276`).
2. `Rule::unique(Model::class)` produce `<Classe>.<tabella>` (`DatabaseRule.php:61`); `DatabaseManager::makeConnection()` legge la config e poi `$extensions[$nome]`.
3. Sushi scrive solo la config con `:memory:` (`Sushi.php:137`), quindi il lookup per nome apre un SQLite nuovo e vuoto, non `$sushiConnection`.
4. Non compare con la cache su file (config = file vero). Compare sempre senza cache: default per `getRows()` e scelta di `SushiToJson`.

Non era "tabella assente nel database": il blocker B5 della story Sigma lo leggeva cosi', e la cura MySQL non lo avrebbe risolto per i modelli Sushi.

## Cosa cambia

| File | Modifica |
| --- | --- |
| `Traits/SushiConnectionByName.php` (nuovo) | `bootSushiConnectionByName()` registra `DB::extend(static::class, ...)` che restituisce `resolveConnection()`, con resolver pigro e `Assert::isInstanceOf(Connection)` |
| `Traits/SushiToJsons`, `SushiToCsv`, `SushiToPhpArray` | `use SushiConnectionByName;` dopo `use Sushi;` |
| `Traits/SushiToJson` | stessa riga; il resto del file e' in riscrittura da parte di un altro editor e non e' stato toccato |
| Sigma `Models/WebService.php` | `$schema` (id, name, created_by, updated_by, created_at, updated_at), tolto `use \Sushi\Sushi;` ridondante, tolti 4 `use` inutilizzati |

Patch pronta per la lettura del JSON (validata su HEAD, da applicare a `SushiToJson` quando la riscrittura e' stabile):

```php
// in getSushiRows() e loadExistingData(), al posto di json_decode(file_get_contents($path), true):
$data = json_decode($this->readJsonContent($path), true);

// nuovo helper privato
private function readJsonContent(string $path): string
{
    $content = file_get_contents($path);

    return trim($content) === '' ? '[]' : $content;
}
```

Un file vuoto vale "nessun record". Un JSON malformato resta un errore: un `catch (JsonException) { return []; }` nasconde la corruzione, contraddice il test `it throws exception when json data is invalid` e non aiuta, perche' `create` poi rifiuterebbe comunque di sovrascrivere.

I 21 rossi sono identici in A (preesistenti); i 32 saltati sono "DB tenant non raggiungibile", quindi la copertura di questa regressione e' parziale.

## 2026-10-07 - PHPStan `trait.unused`: il trait non era codice morto

Fase BMAD: Dev + Docs (cluster PHPStan, modulo Tenant).

**Scopo del codice.** `SushiConnectionByName` lega il nome di connessione di un modello Sushi (la classe stessa) all'istanza SQLite viva. Senza, `Rule::unique`/`Rule::exists` (anche quelle di Filament) e `DB::connection($classe)` aprono un `:memory:` vuoto e falliscono con "no such table". Non si usa nei modelli: lo includono i quattro trait `SushiToJson`, `SushiToJsons`, `SushiToCsv`, `SushiToPhpArray`.

**Sintomo PHPStan.** `Trait Modules\Tenant\Models\Traits\SushiConnectionByName is used zero times and is not analysed` (`trait.unused`).

**Causa radice.** Persa la cablatura, non il trait. Il commit `90acbda` del repo del modulo (2026-10-07) ha aggiunto il trait, il test `tests/Unit/Traits/SushiConnectionByNameTest.php` (dataset sui 4 trait) e le sonde `SushiToCsvConnectionProbe` / `SushiToPhpArrayConnectionProbe`, ma i quattro trait fratelli sono rimasti al commit `c106bc2` (2026-09-24), cioe' senza la riga `use SushiConnectionByName;` prevista dalla tabella "Cosa cambia". Plausibile origine, dalla sezione "Cosa cambia": `SushiToJson` era in riscrittura da un altro editor e le modifiche locali ai fratelli non sono arrivate nel commit. Conseguenza: bug del sintomo ancora presente su tutti i modelli Sushi che usano i trait Tenant (`Cms\Section`, `Menu`, `Attachment`, `Page`, `PageContent`; `User\SocialProvider`; `Xot\InformationSchemaTable`; `Geo\Comune`) e tutti i 9 test del trait destinati a fallire.

**Fix (in avanti).** `use SushiConnectionByName;` subito dopo `use Sushi;` nei quattro trait. Il trait resta com'era; aggiunto solo un paragrafo di docblock che dice chi lo include. Nessuna soppressione PHPStan.

**Incidente di processo.** Durante lo studio il file e' risultato cancellato dal working tree, con lock di `codex-main` (task `phpstan-errors-29`), verosimilmente per far sparire l'errore `trait.unused`. La cancellazione non e' giustificata: esistono test, fixture, doc (`bmad/sushi-model-pitfalls.md`) e modelli host reali in Cms, User, Xot e Geo. Atteso il rilascio del lock, il file e' stato ricreato con lo stesso contenuto (patch in avanti, nessun `git restore`). Se l'altro agente lo cancella di nuovo, i quattro trait fratelli andrebbero in errore fatale al caricamento: non rimuovere il file senza prima togliere gli `use`.

**Verifica.**
- `phpstan analyse` (config progetto) su trait, `Modules/Tenant/app/Models`, `app/Contracts`, `tests/Unit/Traits`, `tests/Unit/Fixtures` e sui modelli host di Cms, User, Xot, Geo: nessun errore.
- Pest `SushiConnectionByNameTest`: non eseguibile in questo ambiente (`Unknown database 'fixcity_data_test'`, MariaDB di test assente, stesso errore prima e dopo). Sostituito da uno script di sonda fuori repo che usa i modelli reali: `DB::connection($classe) === resolveConnection()` e `Rule::unique` danno esito corretto per `SushiToJson`, `SushiToCsv`, `SushiToPhpArray`; `SushiToJsons` risolve la connessione viva (nessuna riga di tenant, quindi il duplicato non c'e'). Controllo negativo con un modello Sushi puro: "no such table".

**Seguiti.**
- I modelli con `use Sushi;` puro (`Cms\Conf`, `Cms\Module`, `Geo\Region`, `Geo\Province`, `Geo\Locality`, `Lang\TranslationFile`, `Tenant\TenantDomain`) hanno ancora il bug se validati con `unique`/`exists`: aggiungere `use SushiConnectionByName;` solo dove serve quella validazione (fuori scope di questo fix).
- `Geo\Models\Traits\SushiToJsons` ha lo stesso nome del trait Tenant ma e' un'altra implementazione (190 righe contro 217) e non include la cura: da riconciliare.
- Restano da eseguire i test del trait quando il DB di test e' disponibile.
