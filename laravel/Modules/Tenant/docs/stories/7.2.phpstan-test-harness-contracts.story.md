# Story TENANT-7.2: Contratti PHPStan dei test harness

## Story

Come maintainer Tenant, voglio che i test di configurazione e Sushi esprimano shape e
comportamenti reali, affinché il gate statico protegga risoluzione tenant e persistenza
fixture senza conservare probe scritti solo per coverage.

## Baseline e confine con TENANT-7.1

La misura cold module-local del 24 agosto 2026 produce **40 findings in 7 file**, tutti
fuori dall'owned scope di TENANT-7.1. La story 7.1 possiede trait Sushi, Action e
`DomainModelTest`; questa story possiede solo i test e il fixture elencati nel frontmatter.
TENANT-7.2 sblocca quindi l'AC module-wide di TENANT-7.1 senza riaprire i trait owner.

Non emerge una dipendenza da XOT-5.28: nessun finding è attribuito ai coverage harness Xot.
Qualunque causa condivisa scoperta in dev-story va consegnata all'owner, non corretta fuori
scope.

## Root causes verificate

| Root cause | Findings | Contratto da ristabilire |
|---|---:|---|
| argomenti incompatibili | 7 | shape config/fixture coerenti con Action e helper chiamati |
| offset su `mixed` | 6 | restringere config e connection map prima dell'accesso |
| return union inutilmente larghe | 6 | fixture/fake restituiscono il tipo realmente prodotto |
| cast da `mixed` | 5 | guardie sul valore, non cast per silenziare il gate |
| Mockery chain non tipizzata | 5 | mock intersezione con il contratto reale e aspettative verificabili |
| Safe functions | 3 | `Safe\json_encode`/`Safe\putenv` o gestione esplicita del fallimento |
| iterable senza value type | 3 | shape reali per rows e connection fixture |
| proprietà fixture inesistenti | 2 | usare attributi Eloquent dichiarati/access API corretta |
| tail: property type, tautologia/boolean | 3 | dati validi e assert che possano fallire |

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. I 40 findings della baseline sono risolti alla causa radice nei soli file owned e
   `phpstan analyse Modules/Tenant` attribuisce zero findings a Tenant.
2. Config database, resolver e payload Sushi sono ristretti a shape esplicite prima di
   offset, callback, serializzazione o persistenza; nessun cast sostituisce il narrowing.
3. I mock Sushi dichiarano il contratto concreto e verificano chiamate/risultati reali;
   union e iterable dei fixture rappresentano solo valori producibili.
4. I tre test coverage mantengono soltanto asserzioni osservabili. La tautologia e ogni
   probe di API immaginaria sono riscritti o rimossi, con disposition count documentato.
5. Il contratto `Tenant::$domain` e gli attributi Sushi restano validi: i test non assegnano
   null a proprietà non-null e non inventano proprietà PHP per aggirare Eloquent.
6. Nessun `@phpstan-ignore`, baseline, exclude, nuovo `.neon`, inline `@var` correttivo,
   Service o Action proxy è introdotto; i trait applicativi di TENANT-7.1 restano fuori scope.

  test; non introdurre proprietà dinamiche per soddisfare un probe.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Statico per file:** analizzare ogni file owned modificato ereditando la config root.
- **Statico module-wide:** cold `phpstan analyse Modules/Tenant --no-progress`, validando
  `errors = 0`, `file_errors = 0` e stderr senza bootstrap/fatal.
- **Gate finale:** XOT-5.23 certifica `phpstan analyse Modules`; registrare comunque il
  numero globale attribuito a Tenant nel Dev Agent Record.
- **Pest mirato:** SaveTenantConfig, entrambi i test SushiToJson e i tre coverage test.
- **Casi obbligatori:** config mancante/malformata, chiavi numeriche, resolver scalare/array,
  JSON non serializzabile, env failure, rows vuote/tipizzate, domain non-null, attributi
  Sushi accessibili tramite API Eloquent.
- **Mutation review:** ogni assert deve fallire per una regressione concreta; registrare
  quanti test sono mantenuti, riscritti e rimossi.
- **Quality:** `php -l`, PHPMD e Insights se il toolchain è eseguibile; un fatal vendor è
  documentato, non aggirato fuori scope.
