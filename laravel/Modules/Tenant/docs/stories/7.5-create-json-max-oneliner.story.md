## 2026-11-03: `max` senza cast di `mixed`, chiave di update solo int o string

Dopo il pull PHPStan segnalava due errori nati dal merge `db091faf` (2026-11-01), che aveva tenuto le correzioni locali del 2026-10-19 al posto dei due `Assert::integer` di upstream:

- `CreateJsonFileByRecordAction`: `(int) max(Arr::pluck(...) ?: [0])` faceva il cast di un `mixed` (`cast.int`). Ora gli id passano da `SafeIntCastAction::cast(...)` e il nuovo id e' `max([0, ...$ids]) + 1`. Restano accettati gli id letti come stringhe numeriche (`'1'`), che `Assert::integer` rifiutava; lo `0` iniziale copre il file vuoto. Tolto l'import `Webmozart\Assert\Assert`, gia' inutilizzato.
- `UpdateJsonFileByRecordAction`: `Assert::scalar($key)` lasciava passare `bool` e `float` come chiave di array (`offsetAccess.invalidOffset`). Ora `$key = Assert::validArrayKey($record->getKey())`: int o string, quindi le chiavi UUID del 2026-10-19 restano valide.

Test nuovo: `tests/Unit/Actions/Json/JsonFileByRecordActionsTest.php` (id stringa numerica -> `max + 1`, file vuoto -> id 1, update della sola riga con la stessa chiave). Usa la fixture `tests/Fixtures/TestSushiModelForPath.php` su un file temporaneo, senza salvare il modello. La fixture casta `id` a intero, quindi il caso UUID non e' coperto qui.

Verifica: PHPStan sull'intero progetto `[OK] No errors`; Pint passa; `pest --test-directory=Modules/Tenant/tests` sul test nuovo: 3 passed.

Nota 2026-11-03 (seconda passata): in `UpdateJsonFileByRecordAction` i due commenti datati in testa al file sono stati sostituiti da un commento sul perche' accanto a `Assert::validArrayKey`. La storia resta qui: il 2026-10-19 `Assert::integer($key)` era stato allargato per accettare chiavi UUID e cosi' sparivano 256 errori nel log. Nel test gli array sono a una chiave per riga e la cartella temporanea si cancella in un `finally`.
