# 5.3: Git LFS: backfill 11 missing image objects

**Story ID:** 5.3
**Epic:** 5: Code Quality & Infrastructure
**Slug:** git-lfs-backfill
**Status:** backlog

## Story

As the DevOps owner accountable for image assets not 404ing in PDF exports and the admin UI,
I want every tracked image object audited and, where broken, repaired back to real committed binary content,
so that NFR-OP-002's underlying integrity goal: no missing/unrecoverable image objects: is met using the project's current, actually-enforced no-Git-LFS mechanism instead of a contradicted, no-longer-applicable LFS backfill.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. All image binaries implicated by NFR-OP-002's "11 total tracked" image objects are located and audited: each is confirmed to be real git blob content, not LFS pointer text and not a hybrid pointer+payload blob. [Source: prd.md#NFR-OP-002: "Backfill: recover/re-upload 4 missing image objects (11 total tracked)"; Source: docs/wiki/rules/no-git-lfs.md: "Blob ibrido: puntatore e contenuto nello stesso file... Non e' ne' un puntatore valido ne' un [valid file]"]
2. Any image found to be a pure LFS pointer (first committed line matching `version https://git-lfs.github.com/spec/v1`) or a hybrid pointer+payload blob is repaired by replacing it with the real binary content: recovered from `.git/lfs/objects/` cache, a historical commit with real content, or re-upload from the original source: and recommitted as a normal git blob. [Source: docs/wiki/rules/no-git-lfs.md: "In un conflitto tra un lato puntatore LFS e un lato con contenuto reale: tenere sempre il contenuto reale, mai il puntatore"; "La riparazione e' riscrivere il file col solo payload e committarlo"]
3. After repair, `bash bashscripts/tools/check-no-git-lfs.sh` exits `0` for the whole monorepo, confirming zero committed LFS pointer text, zero active `filter=lfs` directives, and zero local LFS config/hooks remain anywhere the check scans. [Source: bashscripts/tools/check-no-git-lfs.sh: "Uscita: 0 pulito, 1 tracce di lfs trovate."]
4. A written audit report enumerates each tracked image object named or implied by NFR-OP-002, its repair status (already-clean / repaired / not-found-needs-re-upload), and the recovery method used. [Inference: "backfill" implies an accounted-for list of the specific objects touched, not just a pass/fail signal]
5. No `.gitattributes` file anywhere in the monorepo gains a `filter=lfs`, `diff=lfs`, or `merge=lfs` directive as part of this repair: every affected image remains (or becomes) a normal `binary !filter` git blob per the project's current no-LFS policy. [Source: docs/wiki/rules/no-git-lfs.md: "Git LFS non si usa in questo progetto... Vietato: aggiungere filter=lfs diff=lfs merge=lfs in un qualsiasi .gitattributes"]

## Tasks / Subtasks

- [ ] Enumerate the tracked image objects referenced by NFR-OP-002 (search Media module and other module image paths for pointer-signature or unexpectedly small/large binaries) (AC: #1, #4)
- [ ] For each candidate, inspect the first committed line for the LFS pointer signature, and check for the hybrid pointer+payload pattern (committed size = payload + pointer header) described in `no-git-lfs.md` (AC: #1)
- [ ] Repair each broken file found: source real content from `.git/lfs/objects/<oid[0:2]>/<oid[2:2]>/<oid>`, a historical commit with real content, or re-upload; recommit as a plain blob (AC: #2)
- [ ] Run `bash bashscripts/tools/check-no-git-lfs.sh` and confirm exit code `0` (AC: #3)
- [ ] Write the audit report listing every object, its status, and its recovery method (AC: #4)
- [ ] Confirm `git grep -n "filter=lfs" -- '*.gitattributes' | grep -v ':[0-9]*:#'` returns nothing new introduced by this story (AC: #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Sourced requirement (verbatim):** "NFR-OP-002: MUST: Git LFS Validation / Backfill: recover/re-upload 4 missing image objects (11 total tracked) / CI gate: `git lfs ls-files` verifies all pointers have remote objects / Quota: 2TB LFS quota (current 1TB insufficient for 5-year growth) / Recovery: document LFS restore procedure; test quarterly." [Source: prd.md#NFR-OP-002]
- **ADR grounding:** "ADR-010 | Deploy EU-Only with Health Checks, Backups, and LFS Validation | Accepted | NFR-REL-001, NFR-SEC-004, NFR-OP-002": "Decision: ...Add... CI validation for Git LFS pointers..." [Source: architecture.md#adr-010]
- **CONFLICT CALLOUT (read before implementing):** `NFR-OP-002` and `ADR-010` describe an active Git-LFS-based strategy: tracking images in LFS, backfilling missing LFS objects, and gating CI on `git lfs ls-files`. The project's current, dated-later, actually-enforced policy is the **opposite**: "Git LFS non si usa in questo progetto... vale per il repo root, per `bashscripts/` e per ogni path di moduli e temi." Rationale recorded in the same doc: "Gli asset del progetto sono piccoli (~10 MB totali): LFS non porta beneficio," and LFS "ha prodotto ripetutamente pointer orfani" causing broken images/SVGs and rejected pushes (`GH008: unknown Git LFS objects`) in the multi-org (`laraxot`/`provtv`) workflow. [Source: docs/wiki/rules/no-git-lfs.md] This story satisfies NFR-OP-002's underlying business intent: no missing/broken image objects: via the currently-enforced mechanism (real git blobs, `binary !filter`), not by re-introducing Git LFS. Treat `no-git-lfs.md` as authoritative over `NFR-OP-002`'s literal LFS-specific wording for *how* integrity is achieved; NFR-OP-002 still governs *what* must be true (no missing image objects).
- **PRD figure precision note:** the PRD's own NFR-OP-002 text says "recover/re-upload **4** missing image objects (**11** total tracked)": the epics.md story title's "backfill 11 missing image objects" overstates the missing count; only 4 of the 11 tracked objects are stated as missing. AC #1 and #4 therefore scope the *audit* to all 11 tracked objects but expect repair action on however many are actually found broken (up to 4 per the PRD figure, though the live count may differ by the time this story runs). [Source: prd.md#NFR-OP-002: "recover/re-upload 4 missing image objects (11 total tracked)"]
- **Recovery mechanics (verbatim):** "Se entrambi i lati sono puntatori, recuperare dall'oggetto in cache locale: `oid=$(sed -n 's|^oid sha256:||p' path/to/file.svg | head -1); cp \".git/lfs/objects/${oid:0:2}/${oid:2:2}/$oid\" path/to/file.svg`." Hybrid-blob detection: "il blob committato pesa esattamente il payload piu' l'intestazione (2861 contro 2732 byte)... La riparazione e' riscrivere il file col solo payload." [Source: docs/wiki/rules/no-git-lfs.md]
- **Verification tool already exists:** `bashscripts/tools/check-no-git-lfs.sh`: "Verifica che git-lfs non sia in uso in QUESTO progetto... Uscita: 0 pulito, 1 tracce di lfs trovate." This story does not need to write a new checker; it repairs data and confirms the existing one still passes. [Source: bashscripts/tools/check-no-git-lfs.sh]
- [Inference] The exact filenames/paths of the 11 tracked image objects are not named in any source document (PRD, architecture, or Media module docs: a targeted search of `laravel/Modules/Media/docs/module.md` found no enumeration). Task #1 (enumeration) is therefore a discovery step, not a lookup, and the Owned File/Module Scope below cannot name the specific image paths in advance.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** this is a one-time data-repair/audit operation, not application logic: verification is via the existing shell checker (`check-no-git-lfs.sh`) plus manual/scripted content inspection (pointer-signature grep, byte-size hybrid check), not new Pest unit tests. A lightweight regression assertion (shell or Pest) confirming zero pointer-signature matches remain is reasonable to leave behind, but is not the primary verification mechanism.
- **Fixtures:** none beyond the repository's own git history and the `.git/lfs/objects/` cache (if not yet purged) as a recovery source.
- **Scenarios to prove each AC:**
  - AC #1: run a pointer-signature grep (`git grep -l "version https://git-lfs.github.com/spec" HEAD`) across all module/theme image paths; confirm the enumerated 11 objects are all accounted for as clean or flagged.
  - AC #2: for each repaired file, confirm its post-repair `sha256sum` matches a known-good source (cache object OID, or a historical commit's real-content blob).
  - AC #3: run `bash bashscripts/tools/check-no-git-lfs.sh`; confirm exit code `0` and "OK: nessuna traccia di git-lfs nel progetto." output.
  - AC #4: confirm the audit report lists all 11 objects with a status and recovery method for each.
  - AC #5: `git grep -n "filter=lfs" -- '*.gitattributes' | grep -v ':[0-9]*:#'` returns empty (only the prototype's forbidding comment line may mention the string, and that's excluded by the grep).
- **Edge cases:** an image whose real content cannot be recovered from any source (LFS cache already purged, no clean historical commit, original source unavailable): must be flagged "not-found-needs-re-upload" in the report rather than silently left broken; an image clean in the current working tree but still broken in an older reachable commit/tag (repair should not stop at HEAD if other refs matter); a file that is byte-identical to a pointer's expected hybrid size by coincidence but is actually a legitimately small real image (avoid false-positive "repair" of a genuinely clean file).
