# 5.4: LFS validation in CI

**Story ID:** 5.4
**Epic:** 5: Code Quality & Infrastructure
**Slug:** lfs-ci-validation
**Status:** backlog

## Story

As the tech lead accountable for the project's no-Git-LFS policy actually holding on `dev`,
I want a dedicated CI job that runs the existing `check-no-git-lfs.sh` verification on every push and pull request,
so that a reintroduced LFS pointer, hybrid blob, or `filter=lfs` directive is caught and blocked before merge instead of relying on manual review.

## Acceptance Criteria

<!-- LOCKED. External dev tools must not edit Acceptance Criteria. -->

1. A new workflow file `.github/workflows/no-git-lfs.yml` runs `bash bashscripts/tools/check-no-git-lfs.sh` on every push and pull request targeting `dev`. [Source: bashscripts/tools/check-no-git-lfs.sh: existing, working checker; Source: docs/wiki/rules/no-git-lfs.md: describes this check as the project's LFS-absence verification mechanism]
2. The workflow job fails (the GitHub Actions job goes red, no trailing `|| true`) when the script detects any of its four violation classes: an active `filter=lfs`/`diff=lfs`/`merge=lfs` directive in any `.gitattributes`, a committed file starting with the LFS pointer signature, a local `filter.lfs.*` git config section, or an LFS-related git hook. [Source: bashscripts/tools/check-no-git-lfs.sh]
3. This story does not modify `.github/workflows/ci.yml` or `.github/workflows/quality.yml`: it creates only the new, separate `no-git-lfs.yml` file. [Source: laravel/Modules/Xot/docs/stories/5.6.ci-quality-gates.story.md: Owned Scope: "SHARED boundary with 5.4: 5.6 owns `ci.yml`; 5.4 owns a new, separate `.github/workflows/no-git-lfs.yml` file"]
4. The required-status-check name for this new job (e.g. `no-git-lfs`) is documented in this story's Dev Notes handoff for whoever configures branch protection on `dev`. [Inference: same pattern as 5.6 AC #3, since a CI job only blocks merge once branch protection names it as required]
5. The workflow itself never installs, configures, or invokes Git LFS (no `git lfs install`, no `actions/checkout` with `lfs: true`): it only validates LFS's continued absence. [Source: docs/wiki/rules/no-git-lfs.md: "Git LFS non si usa in questo progetto"]

## Tasks / Subtasks

- [ ] Create `.github/workflows/no-git-lfs.yml` with a checkout step and a run step invoking `bash bashscripts/tools/check-no-git-lfs.sh`, triggered on `push` and `pull_request` to `dev` (AC: #1)
- [ ] Confirm the run step has no trailing `|| true` so the script's exit code propagates to the job result (AC: #2)
- [ ] Confirm no lines in `.github/workflows/ci.yml` or `.github/workflows/quality.yml` are touched by this story's diff (AC: #3)

- [ ] Review the new workflow YAML and confirm it contains no `git lfs install` step and no `lfs: true` checkout option (AC: #5)

## Dev Notes

<!-- LOCKED. External dev tools must not edit Dev Notes. -->

- **Sourced requirement (verbatim):** "NFR-OP-002: MUST: Git LFS Validation ... CI gate: `git lfs ls-files` verifies all pointers have remote objects." [Source: prd.md#NFR-OP-002]
- **CONFLICT CALLOUT (read before implementing): same conflict already flagged in story 5.3:** the PRD's literal CI-gate wording (`git lfs ls-files`) presumes Git LFS is actively used and its CLI is installed in the CI runner. The project's current, actually-enforced policy is the opposite: Git LFS is forbidden monorepo-wide. [Source: docs/wiki/rules/no-git-lfs.md: "Git LFS non si usa in questo progetto... vale per il repo root, per `bashscripts/` e per ogni path di moduli e temi."] Running `git lfs ls-files` in CI would require installing the LFS CLI, which itself would contradict the no-LFS policy and risk reintroducing the "pointer orfani" failure mode the policy exists to prevent. This story therefore implements NFR-OP-002's CI-gate *intent*: catch broken/missing LFS-related artifacts before merge: using the project's actual enforcement mechanism (`check-no-git-lfs.sh`), not the PRD's literal `git lfs ls-files` command.
- **Existing script being wired in (verbatim description):** "Verifica che git-lfs non sia in uso in QUESTO progetto... Uscita: 0 pulito, 1 tracce di lfs trovate." Four checks: no active `filter=lfs` in any `.gitattributes` (excluding rule-doc comment lines), no committed file whose first line is the LFS pointer signature `version https://git-lfs.github.com/spec/v1`, no local `filter.lfs.*` git config section in any nested repo, no LFS-related hooks (`pre-push`, `post-checkout`, `post-commit`, `post-merge`) installed. [Source: bashscripts/tools/check-no-git-lfs.sh]
- **Wiki doc's CI claim was aspirational, not real, prior to this story:** `docs/wiki/rules/no-git-lfs.md` describes this verification as something that also runs in CI, implying a workflow of this kind should exist. A repo-wide glob of `.github/workflows/*.yml` (28 files) prior to this story confirmed no `no-git-lfs.yml` file existed: the doc's description was ahead of the actual repository state. This story is what makes the doc's own description true. [Source: docs/wiki/rules/no-git-lfs.md; Inference from absence confirmed via a full `.github/workflows/*.yml` glob]
- **ADR grounding:** "ADR-010 | Deploy EU-Only with Health Checks, Backups, and LFS Validation | Accepted | NFR-REL-001, NFR-SEC-004, NFR-OP-002": "Decision: ...Add... CI validation for Git LFS pointers...": same ADR cited by story 5.3; this story is the CI-side half of that decision, 5.3 is the data-repair half. [Source: architecture.md#adr-010]
- **Shared-boundary confirmation:** story 5.6 (`ci.yml`) has already reserved `no-git-lfs.yml` as a distinct file this story owns, avoiding a merge conflict between the two CI-facing stories. [Source: laravel/Modules/Xot/docs/stories/5.6.ci-quality-gates.story.md]
- [Inference] This story does not need to install the Git LFS CLI on the CI runner, since `check-no-git-lfs.sh` only inspects committed file content, `.gitattributes`, local git config, and hooks: none of which require the `git-lfs` binary to be present.

## Testing

<!-- LOCKED. External dev tools must not edit Testing. -->

- **Test type:** CI workflow verification: this is a YAML/workflow change, not application code; verification is via observed GitHub Actions run outcomes, consistent with how 5.6 verifies its own workflow edits.
- **Fixtures:** none new: the script under test already exists and is exercised directly.
- **Scenarios to prove each AC:**
  - AC #1: push a branch that only adds `.github/workflows/no-git-lfs.yml`; confirm the job runs automatically on that push and on a subsequent pull request.
  - AC #2: on a throwaway scratch branch, commit a file whose first line is the literal LFS pointer signature text in a path outside any real module (e.g. a temp fixture file removed before merge); confirm the job fails; remove it and confirm the job passes.
  - AC #3: `git diff --stat` against `dev` for the story's branch shows only `.github/workflows/no-git-lfs.yml` added: `ci.yml` and `quality.yml` are byte-identical to before.
  - AC #4: confirm the Dev Notes/handoff text naming `no-git-lfs` as the required check is present and legible for whoever configures branch protection.
  - AC #5: manual review of the new YAML confirms no `git lfs install` or `lfs: true` checkout option appears anywhere in the file.
- **Edge cases:** a legitimate documentation file (like `no-git-lfs.md` itself) that mentions `filter=lfs` in prose as a *forbidden example* rather than an active directive: the underlying script already excludes rule-doc comment lines from its `.gitattributes` check, so this workflow should not need extra handling, but the dev agent should confirm that exclusion still holds when run inside the CI runner's checkout (not just locally); a fork-based pull request where checkout behavior or permissions differ from a same-repo push; the workflow running against a fresh, shallow CI clone rather than a full local working tree with `.git/lfs/objects/` cache: the script's checks (pointer signature, `.gitattributes`, git config, hooks) are all content/config checks that work identically on a shallow clone, so this should not be a blocker, but is worth a first-run sanity check.
