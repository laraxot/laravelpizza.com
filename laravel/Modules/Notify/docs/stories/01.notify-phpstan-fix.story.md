## Solution

Poiche' non c'erano errori PHPStan da correggere, il lavoro si e' spostato
sulle richieste esplicite collaterali del task (mixed reduction, UserContract)
con verifica PHPStan ad ogni modifica (nessuna regressione ammessa):

1. **`app/Notifications/TicketAssignedNotification.php`**: unico file in
   `app/` che referenziava il model concreto `Modules\User\Models\User`
   invece del contratto:
   - `public User $assignedBy` → `public UserContract $assignedBy`
     (`Modules\Xot\Contracts\UserContract`), stesso pattern gia' in uso in
     `app/Datas/RecordNotificationData.php` e
     `app/Models/Policies/MailTemplatePolicy.php`.
   - `public mixed $ticket` → `public object $ticket` (nessun model `Ticket`
     nel modulo; i chiamanti passano un `Model` Eloquent o un oggetto
     generico: vedi test). Allineato al pattern gia' presente nella classe
     gemella `TicketStatusChangedNotification` che usa `object $notifiable`.
   - `via(mixed $notifiable)`, `toMail(mixed $notifiable)`,
     `toArray(mixed $notifiable)` → `object $notifiable` (la classe base
     `Illuminate\Notifications\Notification` non dichiara questi metodi, zero
     vincoli di contravarianza; stesso pattern della classe gemella).
   - **Bug latente scoperto dal narrowing**: `toArray()` dichiarava
     `@return array{assigned_by: string}` ma `UserContract::$id` e'
     `string|null` (vedi docblock del contratto): con `User` concreto
     PHPStan non aveva un tipo preciso per `->id` e non lo aveva mai
     rilevato. Corretto a `array{assigned_by: string|null}`: riflette la
     realta' del contratto invece di promettere una garanzia non vera.
2. Verificato che non esistono altri usi di `Modules\User\Models\User` /
   `Modules\...\Models\Profile` concreti in `app/` (grep mirato, 0 risultati
   residui).
3. **`tests/Unit/Actions/BuildMailMessageActionTest.php`**: durante la
   verifica Pest e' emerso un `FAIL` pre-esistente (non causato da questa
   story, file mai toccato prima, gia' rotto nell'ultimo commit su `dev`):
   `it has required imports` asseriva la presenza letterale di `use
   Spatie\LaravelData\DataCollection;` nel sorgente di
   `BuildMailMessageAction.php`, import che quella classe non ha (il
   parametro `$attachments` e' `array<int, AttachmentData>|null`, non una
   `DataCollection`). Corretto sostituendo l'assert con un import
   realmente presente e usato dalla classe
   (`Modules\Notify\Datas\NotifyThemeData`).
4. Non toccati gli altri 103 file con `mixed` in `app/`: la maggior parte e'
   gia' stata analizzata e motivata in `4.28.mixed-type-reduction.story.md`
   (contratti multi-provider SMS/WhatsApp/Telegram con shape di ritorno
   eterogenee, bag di config da env, DTO Spatie-Data con `definition()`
   idiomatico): riaprire quell'analisi file-per-file senza un nuovo errore
   PHPStan a giustificarla sarebbe scope creep rispetto al mandato
   "PHPStan L10 fix".

  Workaround tentato: `git replace --graft` sui due commit rotti (li fa
  apparire come radice per la sola lettura/traversal locale, `refs/replace/*`
  restano locali e non vengono mai pushati, nessun hash reale toccato).
  Con il graft attivo, `git status`, `git merge-base`, `git rev-list
  --objects HEAD --not <remote-refs>` e **`git push --dry-run`**
  funzionano tutti puliti (`a876ae18..7406a8ab dev -> dev`, fast-forward,
  dev locale 21 commit avanti). **Ma il push reale fallisce comunque**:

  ```
  error: Could not read 2c641c73c5ab1282c044f3436ac2573cb73d28e0
  fatal: revision walk setup failed
  remote: fatal: early EOF
  error: remote unpack failed: index-pack failed
  ! [remote rejected]   dev -> dev (failed)
  ```

  Motivo: `send-pack`/`pack-objects` (il codice che genera davvero il pacchetto
  da trasferire in rete) **ignora deliberatamente i `replace`/graft** per
  evitare di trasferire storie incoerenti fra cloni diversi: comportamento
  documentato di git, non un bug del workaround. Il graft aiuta solo i comandi
  di lettura/ispezione locale (`status`, `log`, `dry-run`), non il trasferimento
  vero. Riprovato due volte, stesso esito identico entrambe le volte
  (non e' un flake di rete).

  **Conclusione**: con i vincoli dati (niente `--force`, niente rewrite/
  filter-repo della history remota), il push di nuovi commit su
  `laraxot/module_notify_fila5.git` branch `dev` e' **bloccato per chiunque**
  finche' non viene riparato l'oggetto mancante lato remoto (o il proprietario
  autorizza esplicitamente un rewrite). Il commit locale `7406a8ab` (fix
  applicativo + story + coverage) resta integro e pronto su `dev` in locale,
  in attesa che il blocco venga risolto a monte.

### Causa radice (unica, ripetuta 4 volte)

`XotBaseResource::getFormSchema()` (in `Modules/Xot`) e
`XotBaseResourceForm::getFormSchema()` / `XotBaseResourceInfolist::getInfolistSchema()`
(in `Modules/Xot/app/Filament/Resources/Schemas/`) sono **metodi di istanza
`final`**, non statici. Il pattern canonico gia' in uso nel resto della
codebase per invocarli fuori da un contesto Filament e' `app(Class::class)->getFormSchema()`
(vedi `Modules/Xot/app/Filament/Resources/XotBaseResource/RelationManager/XotBaseRelationManager.php:59`
e `Modules/Xot/app/Filament/Resources/RelationManagers/XotBaseRelationManager.php:110`).
Chiamarli con sintassi statica (`ClassName::getFormSchema()`) e' un **errore
PHP reale a runtime** in PHP 8, non solo un finding PHPStan: verificato con
`./vendor/bin/pest` su `NotifyFilamentResourcesCoverageTest.php` prima del
fix: `Error: Non-static method ...::getFormSchema() cannot be called
statically`, 5 test falliti.

File corretti in questa sessione (3, di mia proprieta' esclusiva, verificati
liberi con `bashscripts/lock/check.sh` prima e durante):

1. `app/Filament/Resources/NotificationTemplateResource.php:28` -
   `getPages()` dichiarava `@return array<string, Field>` (import
   `Filament\Forms\Components\Field` mai usato altrove nel file, copia-incolla
   da un altro metodo) ma ritorna `array<string, PageRegistration>` (il tipo
   reale di `parent::getPages()`). Corretto import + docblock. `pint` ha poi
   rimosso a cascata altri 4 import gia' inutilizzati nello stesso file
