# 19.UI: risoluzione dei marker del merge HEAD vs laraxot/dev

**Fase BMAD:** Docs/Review (chiusura del merge, verifica, tracciamento followups)
**Story ID:** 19.UI-merge-conflict-resolution
**Stato:** done (risoluzione); followups aperti elencati sotto
**Precedenti dello stesso problema:** [5.8](./5.8.merge-conflict-markers-cleanup.story.md), [5.12](./5.12.merge-markers-regressione-c89696dc.story.md)

## Problema

Il commit `e7e667b11` (7 ottobre 2026) ha portato nel repository un merge `HEAD` contro `laraxot/dev` con marker di conflitto non risolti. Nel modulo UI i file con marker erano **507 file PHP** (codice, lang, view Blade, test) e **7 file `.md`**. PHPStan non poteva analizzare i file con marker (`phpstan.parse`) e le regole di agnosticismo e le traduzioni erano a rischio.

## Regola di risoluzione adottata

- `HEAD` e' la baseline: il codice con cui `phpstan analyse Modules` termina a zero errori.
- Il lato `laraxot/dev` (upstream, chiamato "theirs") e' adottato **solo se** i simboli che usa esistono nel repository (classi, metodi, chiavi lang, view).
- Dove entrambi i lati hanno contenuto, decide lo strumento (`php -l`, PHPStan, lettura del codice chiamante), non la posizione nel diff.
- Nei docs, nessun lato scelto alla cieca: un solo documento coerente che conserva l'informazione unica di entrambi; versioni "agnostiche" (`<nome progetto>`) preferite alle versioni con nomi di progetto, per la regola di agnosticismo dei moduli.

## Decisioni notevoli (merged e ours)

- `app/Actions/GetUserDataAction.php` (ours): upstream usa `UserContract`, ma il contratto non dichiara `getRoleNames()` e `getAllPermissions()` (undefined method per PHPStan) e `property_exists($user, 'name')` e' sempre falso per gli attributi Eloquent: nome ed email sarebbero vuoti. Tenuta la baseline.
- `app/Enums/TableLayout.php` (ours): upstream aggiunge un `toArray()` valore=>nome che fa shadow di `EnumTrait::toArray()` (valore=>etichetta tradotta).
- `app/Filament/Widgets/OverlookWidget.php` (ours): view impostata nel costruttore con `@var view-string`; l'upstream rischiava `property.phpDocType`. Il comportamento e' identico perche' `XotBaseWidget::__construct()` chiama `resolveView()`.
- `tests/Unit/Enums/TableLayoutEnumTest.php` (ours): upstream eliminava i test su etichette e icone it, che il codice supporta.
- `tests/Feature/ComponentReorganizationTest.php` (ours): mantiene il namespace come gli altri Feature test.

- `app/Models/Collection.php` (merged): docblock da schema con `name` e `type` nullable come da migration `2026_07_15_100001`.
- `app/Providers/UIServiceProvider.php` (merged): corretta la frase falsa "modulo Geo non presente" (`Modules/Geo` esiste, il confine e' in `docs/geo-boundary.md`).
- `app/Filament/Widgets/{DarkModeSwitcherWidget,UserCalendarWidget,RedirectWidget,RowWidget}.php` (merged): upstream piu' `@var view-string` sulla property `$view`.
